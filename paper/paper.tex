\title{Where the Seconds Go:\\[2pt]\large A Host-Memory Law and a Speed Limit for Mixture-of-Experts Decode\\ on One Consumer GPU}
\author{Harshith Kantamneni\\Independent Researcher}
\date{}

\begin{document}
\maketitle

\begin{abstract}
A Mixture-of-Experts (MoE) model too large for one consumer GPU keeps most of its experts in host memory, and every
decoded token waits while some of them are read. We ask where each token's time goes on such a machine and how much of it
any system could remove.
\textbf{(1) A host-memory law.} Time per token is a fixed GPU term plus the expert bytes read from host memory, divided
by the rate of the read paths in use (CPU, PCIe, or both at once). Written on each machine from its own bandwidth probe
before any model run, it predicted \lawN{} configurations of our cache on \lawHosts{} machines with \lawMedian\% median
error. It fails in three cases, and we explain each.
\textbf{(2) A speed limit.} The per-layer Belady optimum with bypass, on routing traces of the measured text, together
with the machine's highest measured host read rate, bounds any exact-routing system at a given GPU expert budget.
Decomposing the gap between that limit and measured speed shows where the remaining seconds go: missing foresight,
GPU efficiency at batch 1, and per-token host work.
\textbf{(3) A system the law implies.} We built an expert cache into llama.cpp. It runs misses on the CPU and sets,
per machine, how many of a layer's missed experts to copy over PCIe instead. At equal GPU memory on one RTX 5090 machine
it decodes gpt-oss-120b \ftLeadGptMin--\ftLeadGptMax\% faster than FreeToken and Qwen3-30B-A3B
\ftLeadQwenMin--\ftLeadQwenMax\% faster, and runs \llamaXMin--\llamaXMax$\times$ as fast as llama.cpp. An ablation
attributes most of the gain to dynamic caching and to the replacement policy.
\textbf{(4) Foresight.} The optimum reads 22--56\% fewer experts from host memory than the best online policy. The
lookahead that closes half of that gap grows as ${\approx}0.5\,(C/k)^{1.4}$ tokens across nine models.
Every prediction was committed before the measurement it predicts.
\end{abstract}

\section{Introduction}
Open-weight Mixture-of-Experts models now carry 30--120\,B parameters and activate a few billion per token; a desktop
GPU has 24--32\,GB. Running such a model at batch 1 therefore means keeping most experts in host DRAM, and each
decoded token then reads its routed experts from one of three places: GPU memory, host memory by the CPU that runs the
expert, or host memory across PCIe into a GPU slot~\cite{ivanov2021datamovement,hoefler2021sparsity}. A line of
systems has built on this: GPU expert caches with demand fetch~\cite{eliseev2023offloading,xue2024moeinfinity,song2024promoe},
CPU execution of misses~\cite{kamahori2024fiddler,ktransformers,zhong2025hybrimoe,huang2025cpugpu,daop2025,dali2026},
per-miss choices between the two~\cite{freetoken}, and expert prediction~\cite{hwang2024pregated,zhu2025preattention,wang2026seqmoe}.
Each reports a speed-up over a baseline of its choosing. None states how fast its machine \emph{could} decode the model
within the same GPU memory, which host parameter decides whether a miss should be copied or computed where it is,
or how much of the remaining time any design could remove.

We answer these questions on consumer hardware (RTX 5090 hosts with desktop CPUs, rented on Vast) with two
models, gpt-oss-120b~\cite{openai2025gptoss} and Qwen3-30B-A3B~\cite{yang2025qwen3}. The method is Hoefler and Belli's~\cite{hoefler2015benchmarking}:
a performance model with bounds, statistically sound comparisons, and every prediction committed to a public repository
before the machine it concerns was started (\cref{app:prereg,app:rules}).

\paragraph{Contributions.}
\begin{itemize}\setlength\itemsep{1pt}
\item \textbf{A host-memory law} (\cref{sec:law}): time per token $=G+\max(X_c/B_c,\,X_p/B_p,\,(X_c{+}X_p)/B_{cp})$,
with host bytes $X$ from the engine's own counters and read rates $B$ from a probe of the machine. Predicted blind on
\lawHosts{} machines, its median error is \lawMedian\% over \lawN{} configurations and \lawDeskMedian\% on the desktop-class
ones; the three places it fails each point at something the law leaves out.
\item \textbf{A speed limit, and where the seconds go} (\cref{sec:limit}): a bound on any exact-routing system with $C$
expert slots per layer, from exact routing traces and measured bandwidths, reported next to every measured speed
(\cref{tab:headline}), and a decomposition of the gap into overlap, foresight, policy, GPU efficiency and host work.
\item \textbf{A system that follows from the law} (\cref{sec:system}): a llama.cpp expert cache whose miss path is
chosen per machine from the law. It leads FreeToken~\cite{freetoken} at every budget we measured, runs
\llamaXMin--\llamaXMax$\times$ llama.cpp at equal GPU memory, and an ablation says which parts matter.
\item \textbf{The value of foresight} (\cref{sec:foresight}): how many host reads knowing future routing would save,
and how far ahead one must know it, across nine models.
\end{itemize}

\paragraph{What we do not claim.} Running missed experts on the CPU~\cite{kamahori2024fiddler,ktransformers},
caching hot experts in GPU memory with CPU-executed misses~\cite{zhong2025hybrimoe,huang2025cpugpu,llamacppdisc24528},
and splitting a layer's misses between the CPU and PCIe~\cite{freetoken,dali2026,daop2025} are all published. Our
system uses these ideas; what is new is the law that says when each path pays on a given machine, the limit it is
measured against, and the measurements.

\section{Setting and Method}\label{sec:setting}
\paragraph{Workload.} Single-request decode. gpt-oss-120b (MXFP4 experts; 36 MoE layers of 128 experts, top-4,
13.25\,MB per expert) and Qwen3-30B-A3B in BF16 (48 layers of 128 experts, top-8, 9.44\,MB per expert). Prompts are
the 30 AIME-25 problems in FreeToken's own benchmark format; each system decodes 256 tokens per problem, greedily,
after one warm-up request on a fixed held-out text, in one session in which the cache carries over between problems.
One client measures every system with FreeToken's own metric, (tokens$-$1) over the time between the first and last
token's arrival.

\paragraph{Machines and probes.} RTX 5090 (32\,GB, 1.79\,TB/s) hosts with desktop CPUs, rented by the hour. Each job
first runs a probe (\texttt{concur}) that reads host memory from $t$ CPU threads, over PCIe with zero-copy kernels and
with the copy engine, and from both at once; FreeToken's own probe (\texttt{ft bench bw}) runs too. We call the CPU
rate at the helper thread count $B_c$, the zero-copy PCIe rate $B_p$ and the combined rate $B_{cp}$. GPU clocks cannot
be locked on these rentals; we report the power limit of each card.

\paragraph{Equal memory.} llama.cpp keeps whole layers' experts on the GPU (\texttt{--n-cpu-moe}~$n$), our cache keeps
$C$ experts of every layer, and FreeToken takes a cache rate; we match the number of experts on the GPU (within
2.5\%) and report measured VRAM. FreeToken preallocates 28.4--30.1\,GiB whatever its rate.

\paragraph{Statistics and protocol.} Ratios are of mean speeds, paired by problem, with 95\% percentile intervals from
10{,}000 bootstrap resamples. Where a system has variants (our FETCH tables, FreeToken's offload and hybrid backends),
a first launch picks each system's faster variant per budget and a second launch, which the comparison uses, runs only
those. Every job's predictions are in the header of its script, committed and pushed before the machine starts.

\section{A Host-Memory Law}\label{sec:law}
With experts partly in host memory, a decode step does two kinds of work: GPU work that every token needs (attention,
dense projections, resident experts, the output head, launches), and reads of the experts that are not resident. The
second is limited by host memory. The CPU reads $X_c$ bytes per token (the experts it runs), PCIe reads $X_p$ bytes
(the experts copied to the GPU, whether on demand or ahead of time), and when both run at once they share the DRAM:
\begin{equation}
T \;=\; G \;+\; \max\!\Big(\frac{X_c}{B_c},\ \frac{X_p}{B_p},\ \frac{X_c+X_p}{B_{cp}}\Big).
\label{eq:law}
\end{equation}
$X_c$ and $X_p$ come from the engine's counters of misses, fetches and admissions, which do not depend on the machine.
$B_c$, $B_p$ and $B_{cp}$ come from the machine's probe. $G$ is one constant per engine and model, fitted once on one
host (4.82\,ms for our cache on gpt-oss-120b, 5.06\,ms for llama.cpp) and then frozen in the repository.

\input{tab_law}

\paragraph{Blind test.} On every later machine the job wrote the law's prediction from its own probe before any model
ran (\cref{tab:law}). Over \lawN{} configurations of our cache on \lawHosts{} machines the median error is \lawMedian\%; on
the \lawDeskN{} configurations of desktop-class hosts it is \lawDeskMedian\% (90th percentile \lawDeskPninety\%). llama.cpp
\texttt{--n-cpu-moe} is predicted within 4\% on the Ryzen hosts, including two Qwen3 configurations predicted on the
headline machine (+3.6\%, +4.0\%).

\paragraph{Where it fails.} Each failure names a term the law leaves out. (i) Configurations that copy misses on demand
(FETCH) are over-predicted by about 12\% on every host with a slow link: the law has no per-layer copy latency.
(ii) llama.cpp on a Core Ultra 7 with 8 performance and 16 efficiency cores runs at 45\% of the law, because it splits
every matrix evenly across its threads; our helpers claim work dynamically and stay on the law on the same machine.
(iii) On a 12-channel EPYC 9655 (559\,GB/s) host memory stops being the limit: a layer with one or two CPU misses
takes 80--200\,$\mu$s, a latency floor of the per-layer hand-off.

\paragraph{What the law says.} Every mechanism in this design space acts only through the bytes read from host memory
per token and the number of read paths in use. A second path adds bandwidth on the hosts we
measured ($B_{cp}$ against $\max(B_c,B_p)$: \secondMin--\secondMax\% on the Ryzen hosts, \secondUltra\% on the
Core Ultra, \secondEpyc\% on the Zen~2 EPYC), and that is the whole gain available to fetching, prefetching or splitting
misses between the CPU and PCIe. Prefetching never reduces the bytes. And the ``host lottery'' is the DRAM: two
rentals of the same CPU differed by 19--22\% in speed, which is 62 against 47\,GB/s of host bandwidth.

\section{The Speed Limit, and Where the Seconds Go}\label{sec:limit}
\paragraph{Bound.} Consider any system that executes the model's exact routing with at most $C$ experts of each layer
resident on the GPU. Per token, each of the $Lk$ routed experts is either served by a resident copy (the GPU reads it
from VRAM) or not, in which case its $S$ bytes are read from host memory once more: by the CPU that runs it, or by the
copy that brings it into a slot. Let $R^\star$ be the reads per token of Belady's MIN with bypass~\cite{belady1966study,hasslinger2018,bypassopt}
applied per layer to the routing trace, the fewest reads of any policy, even one that knows the future. If $c$
experts per token run on the CPU, host memory supplies at least $\max(R^\star,c)\,S$ bytes and the GPU reads the
dense bytes $D$ plus $(Lk-c)\,S$. With everything overlapped,
\begin{equation}
\bar T \;\ge\; \min_{0\le c\le Lk}\ \max\!\Big(\frac{D+(Lk-c)S}{B_{\mathrm{gpu}}},\ \frac{\max(R^\star\!,c)\,S}{B_{\mathrm{host}}}\Big),
\label{eq:limit}
\end{equation}
with $B_{\mathrm{gpu}}$ the GPU's datasheet rate and $B_{\mathrm{host}}$ the highest host read rate the probe measured
by any method (87.5\,GB/s on the headline machine). The bound assumes that an expert run on the CPU is read from DRAM
(the reuse distance of an expert is hundreds of MB, beyond any CPU cache) and drops all latencies. It can exceed the
all-in-VRAM speed, because the CPU's bandwidth adds to the GPU's. The traces are the models' own greedy text on the
30 AIME-25 prompts, templated and tokenised exactly as the server does, with routing recorded teacher-forced by our
llama.cpp instrumentation (job 084).

\paragraph{How far measured systems are from it.} \Cref{tab:headline} reports the limit next to every measured speed:
our system reaches \limitPctMin--\limitPctMax\% of it. \pend{} (job 084)

\paragraph{Decomposition.} \Cref{fig:gap} adds one cost at a time to the bound: (1) no overlap between host reads and
the GPU work that depends on them; (2) no foresight: the best online policy's reads instead of the optimum's; (3) the
deployed policy's reads and read paths, through \cref{eq:law}; (4) the GPU work measured in profiles instead of its
datasheet time; (5) host launch and bookkeeping, measured by a host-side timer; and (6) the residual. At $C{=}32$ with
FETCH the optimum's 4.4\,ms becomes 13.7\,ms measured: overlap +2.0, foresight +3.6, policy +0.2, GPU efficiency +1.6,
host work +0.8, residual +1.1\,ms. Foresight is the largest term that no engineering of read paths can recover
(\cref{sec:foresight}); the GPU term is batch-1 matrix-vector efficiency, about half of the datasheet rate even with
every weight in VRAM (\cref{tab:headline}, last column).

\paragraph{One token, profiled.} On Qwen3 at 43.75\%, Nsight Systems splits a token of our cache (FreeToken) into
4.93 (5.20)\,ms of expert copies over PCIe, 2.29 (2.21) of resident-expert products, 1.65 (1.34) of attention
projections, 0.49 (0.37) of attention, 0.38 of output head and 0.97 (0.40) of norms, small kernels and cache
control; our host-side time is 0.27\,ms (job 079). Neither system overlaps its PCIe copies with GPU compute; doing so
would save 5--10\%. Our extra 0.5\,ms of GPU work comes from unfused batch-1 kernels: we launch 1.6$\times$ as many.

\section{A System That Follows From the Law}\label{sec:system}
\paragraph{Design.} Our cache is a 3{,}700-line patch to llama.cpp. Each MoE layer has $C$ GPU slots. Routing is
decided on the GPU; resident experts run there, and each miss either runs on CPU helper threads, which the GPU
signals through a mailbox in mapped memory, or is copied into a slot and run on the GPU (FETCH). Admission follows a
decayed-frequency score (half-life 16 tokens, an admission margin $\kappa{=}1$) and copies in the background. Sampling
runs on the GPU. The one per-machine decision is the FETCH table $f(n)$: of a layer's $n$ missed experts, how many to
copy. A per-layer form of \cref{eq:law} gives it,
\begin{equation}
T(n,f)=\max\!\big(\tfrac{fS}{B_p}+g,\ [n{>}f](L_c+\tfrac{(n-f)S}{B_c}),\ [0{<}f{<}n]\tfrac{nS}{B_{cp}}\big),
\label{eq:split}
\end{equation}
where $g$ is the GPU's expert work per layer (48\,$\mu$s for Qwen3, 37\,$\mu$s for gpt-oss, from profiles) and
$L_c{=}20\,\mu$s the hand-off; the table picks the $f$ with the smallest $T$ and is computed from the probe when the
job starts.

\paragraph{Choosing the split per machine.} On the headline machine, the law's table beats the fixed table we used
before at every budget of both models, by \lawGainMin--\lawGainMax\% (launch 1). \Cref{tab:split} shows why at one
budget: a single missed expert should run on the CPU (about 155\,$\mu$s, hidden behind the GPU's other experts) rather
than be copied (about 235\,$\mu$s, on the critical path); that entry alone is worth \splitFOne\%. Fetching everything,
FreeToken's offload strategy expressed in our engine, is the worst table, and running everything on the CPU the second
worst. The law's table was within 1\% of the best of five alternatives on launch 1 and tied with it on launch 2. Given
each run's measured misses, \cref{eq:split} orders the tables correctly but overstates their differences about
1.8$\times$. On a contrasting machine, an RTX 5090 in a PCIe~4.0-class slot next to a Core i9-14900K, \pend{} (job 085).

\paragraph{Long outputs.} Our lead does not come from the first 256 tokens. On gpt-oss, on ten held-out hard
problems (AIME 2022, problems 11--15 of both exams) that neither system has finished reasoning about after 2{,}048
tokens (at most \hardAnsMax{} of 10 reach an answer), ours runs \hardAllA, \hardAllB{} and \hardAllC{} times FreeToken
at 11, 25 and 40\% over all 2{,}048 tokens, and \hardLateA, \hardLateB{} and \hardLateC{} over tokens 257--2{,}048
(job 083, listing A); both engines stream one event per token. On Qwen3, over tokens 257--2{,}048 of ten held-out
MATH-500 problems, ours runs \longQwenA{}, \longQwenB{} and \longQwenC{} times FreeToken at 12.5, 25 and 43.75\%.
Both leads are larger than over the first 256 tokens, and turning off FreeToken's prefill overlap, which lends it
cache slots during each prompt, changes its speed by 1\% or less.

\paragraph{Other systems.} Two newer llama.cpp-based systems, Pipelined Sharding~\cite{pipelinedsharding2026} and
leloch's expert cache~\cite{leloch2026}, run gpt-oss-120b at 1.28--1.44$\times$ stock llama.cpp; ours ran 1.42--2.34$\times$
the better of them (job 077). With BF16 weights on a CPU without AMX, KTransformers~\cite{ktransformers} runs Qwen3 at
llama.cpp's speed (job 078); that is not its best setting, which uses AMX and INT4/INT8 weights.

\paragraph{Outputs.} Teacher-forced on fixed text, our system picks the same next token as stock llama.cpp on
\parTopGpt\% (gpt-oss) and \parTopQwen\% (Qwen3) of steps, against \parStockTopGpt\% and \parStockTopQwen\% for stock
llama.cpp with a different layer placement; the loss changes by \parNllGpt\% and \parNllQwen\%. The differences are
floating-point order, not quality, and explain why free-running greedy text diverges early on gpt-oss.

\section{The Value of Foresight}\label{sec:foresight}
The largest gap in \cref{fig:gap} that no read path can close is the policy's ignorance of future routing. On the
models' own sampled text for nine MoE models~\cite{muennighoff2024olmoe,yang2025qwen3,openai2025gptoss}, with the
cache carried across conversations, at 12.5, 25 and 50\% of experts per layer:
\begin{itemize}\setlength\itemsep{1pt}
\item Belady's optimum with bypass reads 22--56\% fewer experts from host memory than the best online policy
(median 40\%, 29 model--budget points).
\item The lookahead needed scales with the cache's turnover time $C/k$ (slots per layer over experts per token): a
policy that sees the next $W$ tokens (Belady within the window, decayed frequency beyond) closes half of the gap at
$W_{50}\approx0.51\,(C/k)^{1.39}$ tokens ($r{=}0.975$ in log--log over 26 points); 90\% needs about $2.5\,C/k$. The
fit is the same on greedy own text and on teacher-forced dataset text (exponents 1.38 and 1.43).
\item Small caches ($C/k\le2$) recover half of the gap with one or two tokens of foresight; gpt-oss-120b at 25\%
($C/k{=}8$) needs about 10 tokens, and at 50\% about 33.
\item Predicting the next layer's experts, the usual form of prediction~\cite{hwang2024pregated,zhu2025preattention},
gives no cross-token foresight: it can raise the hit rate by prefetching but never lowers host bytes, which is what we
measured when we built it.
\end{itemize}
In seconds, for gpt-oss-120b at $C{=}32$ on a desktop host, the best online policy's reads allow 81\,tok/s and the
optimum's 111: foresight is worth up to 37\%. Zhang~\cite{zhang2026reproducible} attributes most of the online-to-optimal
gap to not knowing which resident expert is used furthest in the future; the horizon curve and its conversion to time
are new here.

\section{Related Work}\label{sec:related}
\paragraph{Offloading systems.} Demand-paging systems cache experts per layer and copy misses over
PCIe~\cite{eliseev2023offloading,xue2024moeinfinity,song2024promoe,tang2024hobbit}. CPU-execution systems run
non-resident experts on the host~\cite{kamahori2024fiddler,ktransformers,zhong2025hybrimoe,daop2025,wang2026cloudgrade};
a set-associative GPU cache with CPU-executed misses~\cite{huang2025cpugpu} and a llama.cpp fork~\cite{leloch2026,llamacppdisc24528}
are the closest designs to ours, and FreeToken~\cite{freetoken} and DALI~\cite{dali2026} split each layer's misses
between CPU and PCIe, FreeToken from a closed-form bandwidth model. Pipelined Sharding~\cite{pipelinedsharding2026}
plans sub-layer placement under a VRAM budget. Predictors guess upcoming experts from the previous layer's
state~\cite{hwang2024pregated,zhu2025preattention}, several steps ahead~\cite{wang2026seqmoe}, or a batch's routes
across layers~\cite{expertflow}; Read-ME~\cite{readme2024} makes routing known in advance by decoupling the router and
then caches in Belady's manner. Batched-throughput systems~\cite{cao2024moelightning,yuan2025moelens} and SSD
tiers~\cite{ssdllama,edgezero} are outside our single-request, host-DRAM scope.

\paragraph{Models and bounds.} FreeToken's split and our \cref{eq:split} are both bandwidth models of one layer;
\cref{eq:law} is a whole-token model tested blind across machines. MoE-CAP~\cite{moecap} measures bandwidth
utilisation against a single peak; Qiu et al.~\cite{qiu2026gguf} predict llama.cpp throughput for models run on one
device; Si et al.~\cite{si2026expertcache} derive when a copy pays off. The roofline~\cite{williams2009roofline} is the
single-memory ancestor of our bound, and Hoefler and Belli's rule of showing upper bounds~\cite{hoefler2015benchmarking}
its motivation. Zhang~\cite{zhang2026reproducible} proposes a trace-level evaluation contract for expert caching and
decomposes the online-to-optimal gap in cache blocks; SpecMD~\cite{specmd} benchmarks cache and prefetch policies across
hardware.

\paragraph{Lookahead caching.} Limited lookahead in paging goes back to Albers~\cite{albers1997lookahead}; Hasslinger et
al.~\cite{hasslinger2018} combine Belady within a window with LRU or LFU beyond it for web caches, the policy family we
use to measure the horizon.

\section{Limitations}\label{sec:limits}
\begin{itemize}\setlength\itemsep{1pt}
\item \textbf{Hardware.} One GPU model (RTX 5090; an RTX PRO 6000 for all-in-VRAM runs) and desktop Ryzen and Intel
hosts, rented; GPU clocks could not be locked and power limits differed (400--575\,W). Server CPUs break the law's
bandwidth assumption (\cref{sec:law}).
\item \textbf{Workload.} Single-request decode; AIME prompts, which were also used while developing the system;
greedy decoding. Long outputs are measured on held-out problems. Batch sizes above one and long contexts are not.
\item \textbf{Competitor settings.} FreeToken ran its faster backend per budget with its own bandwidth calibration;
KTransformers ran in a setting that is not its best. Each comparison uses one confirmation launch.
\item \textbf{The bound.} Exact routing only: expert skipping, substitution or deferral change the model and fall
outside it. The bound drops latencies and is loose where the GPU term dominates.
\item \textbf{Constants.} $G$, $g$ and $L_c$ are fitted once and frozen; the per-layer model overstates differences
between FETCH tables about 1.8$\times$.
\end{itemize}

\section{Conclusion}
On a consumer machine, MoE decode time is a fixed GPU term plus host-memory bytes over the rate of the paths that read
them. That law, predicted blind, is accurate to a few percent on desktop hosts; it tells a system which path to use
for a miss on a given machine; and with the optimum's bytes it gives a speed limit that shows how much of each token
remains to be won, and by what. Most of what remains is foresight at small budgets and batch-1 GPU efficiency at large
ones.
