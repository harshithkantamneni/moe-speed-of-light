\author{Harshith Kantamneni\\Independent Researcher}

\begin{abstract}
Frontier-scale Mixture-of-Experts (MoE) models reach desktops only by keeping most experts in host memory, and more than thirty systems now propose policies for which experts to cache on the GPU, how to prefetch them, and where to execute misses. What is missing is a measured ceiling that every policy can be compared against. We contribute three things. \textbf{(1)} A method to record \emph{exact} decode-time routing traces without a GPU: because a causal model's routing of a token depends only on its prefix, teacher-forced prefill streamed one decoder layer at a time reproduces decode routing bit-for-bit (verified against reference implementations on five architectures) while reading each weight once per corpus. On a 2-vCPU, 7\,GB virtual machine we trace OLMoE, Qwen3-30B-A3B, gpt-oss-20b and gpt-oss-120b over four domains. \textbf{(2)} A five-parameter bytes-over-bandwidth model of batch-1 decode that retrodicts \nRows{} published measurements from \nGroups{} independent sources (\tokMin{}--\tokMax{} tok/s, seven models, CPU-only, static CPU offload and PCIe demand fetch) with \cvMedian\% median held-out error. \textbf{(3)} A speed-of-light bound for any per-layer expert placement policy, combining Belady's optimal replacement with Jensen's inequality, and a closed-form reuse threshold $r^\star$ that says when copying an expert to the GPU can pay off at all. The traces show strong short-range locality (\QwenReuseOne\% of Qwen3's selected experts were selected by the previous token, \QwenReuseX$\times$ the uniform rate) but hot-expert sets that do not transfer across domains (Jaccard \QwenJaccard{} vs.\ \QwenJaccardRand{} for random sets), so static ``popular-expert'' pinning calibrated on other data is worse than no pinning. On PCIe~4 desktops, executing a missed expert on the CPU is cheaper than fetching it, and the llama.cpp-style static layer split leaves up to half of the attainable throughput unused, while a plain LRU cache with CPU-executed misses closes most of the gap to the bound, leaving little for predictors to win. Code, traces and the measurement set are released.
\end{abstract}

\section{Introduction}
A 120B-parameter MoE with 4-bit experts occupies \SI{61}{GB}; a consumer GPU has 8--\SI{32}{GB}. Running such models locally therefore means splitting experts between GPU memory and host DRAM, and the resulting decode speed is set almost entirely by where each routed expert's weights live when the router selects it. The literature has responded with many mechanisms: demand fetching into an LRU cache~\cite{eliseev2023offloading}, activation-aware caches and prefetchers~\cite{xue2024moeinfinity,song2024promoe,hwang2024pregated,zhu2025preattention,wang2026seqmoe}, executing misses on the CPU~\cite{kamahori2024fiddler,ktransformers,wang2026cloudgrade,huang2025cpugpu}, mixed-precision or substituted experts~\cite{tang2024hobbit,zhao2025mobile}, and in practice, llama.cpp's static assignment of whole layers' experts to the CPU~\cite{llamacpp}. Recent trace studies disagree on basic questions, such as whether a predictor beats LRU~\cite{zhang2026reproducible,si2026expertcache,wang2026seqmoe}, and one explicitly notes that fewer misses need not mean higher throughput~\cite{zhang2026reproducible}.

We argue that the field lacks a \emph{bound}: for a given model, hardware platform and GPU memory budget, how fast can batch-1 decode possibly be, and how close are the strategies people actually run? A bound turns policy comparisons into a fraction of what is attainable, the way the roofline model~\cite{williams2009roofline} does for kernels. Building one needs (i) routing traces of real models, (ii) a cost model that is \emph{validated} rather than assumed, and (iii) an argument that no policy can beat it. This paper supplies all three, using only public data and a CPU-only virtual machine.

\paragraph{Contributions.}
\begin{itemize}\setlength\itemsep{1pt}
\item \textbf{Exact traces without a GPU} (\cref{sec:traces}). Layer-streaming, teacher-forced prefill yields decode routing exactly; each weight byte is read once per corpus rather than once per token. Bit-exact agreement with reference implementations on five architectures, including MXFP4-packed and sliding-window models.
\item \textbf{A validated decode model} (\cref{sec:model}). Five fitted parameters, every other input taken from datasheets and model configurations. Leave-one-source-out median error \cvMedian\% over \nRows{} published points; an ablation shows which terms matter; two-socket NUMA is the dominant unmodeled effect.
\item \textbf{A speed-of-light bound and $r^\star$} (\cref{sec:bound}). A policy-independent lower bound on time per token, and the minimum reuse count that makes an expert worth copying to the GPU.
\item \textbf{Findings} (\cref{sec:results}). Strong short-range locality, weak cross-domain popularity, CPU execution of misses dominating PCIe fetch on PCIe~4, and a quantified ceiling on what predictors can add.
\end{itemize}

\section{Background and Related Work}
\paragraph{MoE decode is a data-movement problem.} At batch 1, each routed expert is a pair of matrix--vector products whose cost is the bytes of its weights divided by the bandwidth of the memory it is read from. The transformer data-movement view~\cite{ivanov2021datamovement} and sparsity as a first-class efficiency lever~\cite{hoefler2021sparsity} frame MoE placement naturally: the question is which bytes cross which link, and how often.

\paragraph{Offloading systems.} Demand-paging systems keep a per-layer GPU expert cache and copy misses over PCIe~\cite{eliseev2023offloading,xue2024moeinfinity,song2024promoe,tang2024hobbit}; prefetchers predict the next layer's experts~\cite{hwang2024pregated,zhu2025preattention,wang2026seqmoe}. CPU-execution systems run the experts that are not resident on the host~\cite{kamahori2024fiddler,ktransformers,wang2026cloudgrade,huang2025cpugpu}; llama.cpp exposes this as \texttt{--n-cpu-moe} and tensor overrides~\cite{llamacpp}. MoE-Lightning~\cite{cao2024moelightning} and MoE-Lens~\cite{yuan2025moelens} model \emph{batched throughput}; we target single-user latency, where the constraints differ.

\paragraph{Traces and evaluation methodology.} Two recent trace studies analyse expert caching offline~\cite{zhang2026reproducible,si2026expertcache}. The first shows that replay semantics and prompt-template contamination can reverse policy rankings and reports miss rates only; the second studies kernel-managed tiering on GH200. A dense-model study predicts llama.cpp throughput from GGUF metadata, with 36\% decode error on an RTX system~\cite{qiu2026gguf}. We follow the benchmarking-rigour guidelines of Hoefler and Belli~\cite{hoefler2015benchmarking}: report medians and ranges, make the fitted parameters explicit, and hold out whole sources.

\section{Exact Routing Traces Without a GPU}\label{sec:traces}
\paragraph{Observation.} In a causal decoder, the hidden state of token $t$ at every layer is a function of tokens $1..t$ only. The experts that decode selects for token $t$ are therefore exactly the experts that a teacher-forced prefill over the same sequence selects at position $t$, up to floating-point ties. Collecting decode traces does not require running decode.

\paragraph{Layer streaming.} Prefill makes it possible to invert the loop order. Instead of loading every layer for every token, we load \emph{one} decoder layer, push every sequence of the corpus through it, record the router's top-$k$ indices, free the layer and continue. Weights are read once per corpus, activations for the whole corpus stay resident ($\sim$\SI{200}{MB} for 25k tokens), and peak memory is one layer. Safetensors shards are downloaded on demand and deleted once consumed, so disk usage stays at a few shards. Two engineering details matter. First, the MoE sub-block is token-wise, so after per-sequence attention we run it once over the concatenated corpus, touching each expert once per layer. Second, gpt-oss stores experts in MXFP4; a 120B layer would need \SI{13}{GB} in fp32, so we keep the packed tensors and dequantize one expert at a time.

\paragraph{Exactness.} A test compares our per-layer expert selections with the reference \texttt{transformers} implementation on tiny random checkpoints of Qwen3-MoE, OLMoE, DeepSeek-V2 and gpt-oss (both MXFP4-packed and bf16, with sequences longer than gpt-oss's 128-token sliding window). All selections match exactly. For the real models we also report teacher-forced perplexity as an end-to-end check that weights were loaded correctly (\cref{tab:locality}).

\paragraph{Corpus.} We build 160 two-turn conversations from four public datasets: chat (UltraChat), math (NuminaMath-CoT), code (CodeFeedback) and multilingual (Aya, non-English). Each is formatted with the model's own chat template and nothing else, avoiding shared-template contamination~\cite{zhang2026reproducible}. We take about 6k tokens per domain per model. Prompt tokens are prefill; only assistant tokens are decode steps. Conversations are replayed back-to-back in a fixed shuffled order, as one user's session, so cache state carries across conversations and domains.

\paragraph{Cost.} The whole collection ran on a 2-vCPU, \SI{7}{GB} RAM cloud VM with no GPU. Qwen3-30B-A3B (\SI{61}{GB} of bf16 weights) took about 25 minutes of compute over 25k tokens, dominated by the download.

\section{A Bytes-over-Bandwidth Decode Model}\label{sec:model}
\paragraph{Model.} For one decode step,
\begin{equation}
T = \frac{D + X_{g}}{\eta_g B_g} + \frac{X_{c}}{\eta_c B_c} + \frac{X_{f}}{\eta_p B_p} + n_f\,\tau_x + n_h\,\tau_h,
\label{eq:model}
\end{equation}
where $D$ is the per-token dense traffic: attention, shared experts, dense MLPs, routers, norms, LM head and KV-cache reads. $X_g$, $X_c$ and $X_f$ are the routed-expert bytes executed from GPU memory, executed on the CPU, and fetched over PCIe. $B_g$, $B_c$ and $B_p$ are datasheet peak bandwidths of GPU memory, host DRAM (channels\,$\times$\,MT/s\,$\times$\,8\,B) and the host--device link. $n_f$ transfers each pay a fixed latency $\tau_x$, and $n_h$ GPU$\leftrightarrow$CPU hand-offs (one per layer with CPU work) each pay $\tau_h$. Byte counts are exact: we instantiate each architecture on PyTorch's \texttt{meta} device and classify every parameter, and we take bits per weight from the quantization format or from the model file size when the source reports it.

\paragraph{Validation data.} We collected published decode measurements with full hardware descriptions from papers, project documentation and detailed public benchmark threads (\nRows{} points from \nGroups{} groups; each row cites its source and the quoted table or line). They span CPU-only execution on 2- to 12-channel DDR5, static CPU offload (llama.cpp, ik\_llama.cpp, KTransformers and a 2026 research engine~\cite{wang2026cloudgrade}), and demand fetch over PCIe~\cite{eliseev2023offloading}. The models are gpt-oss-20b and 120b, Qwen3-30B-A3B and 235B-A22B, DeepSeek-V3/R1, Kimi-K2 and Mixtral. Rows whose RAM speed was not stated (two), approximate web-UI readings, and VM runs are flagged; two-socket runs of llama.cpp-family engines are held out entirely (below).

\paragraph{Fitting and held-out evaluation.} We fit the efficiencies $\eta$ and latencies $\tau$ by least squares on $\log(\hat{y}/y)$. We evaluate by \emph{leave-one-source-out} cross-validation: all rows from one paper or thread are held out and predicted by a model fit on the rest. The demand-fetch rows come from a single paper, so for them we hold out one GPU at a time. \Cref{tab:ablation} shows the ablation. Bytes over bandwidth with a hand-off term (M0) already reaches \cvMZero\% median held-out error. Adding a per-transfer latency (M1) fixes the fetch rows, because the naive whole-layer copy and the per-expert copy differ in transfer count, not bytes. Per-layer fixed costs (M2) and a server/desktop CPU split (M3) do not improve held-out error. We select M1: $\eta_g=\etaG$, $\eta_c=\etaC$, $\eta_p=\etaP$, $\tau_h=\SI{\tauH}{\micro s}$ and $\tau_x=\SI{\tauX}{ms}$. The fitted $\tau_x$ describes one Python prototype's per-copy overhead: its bulk copies run at $\approx$87\% of PCIe peak while each expert copy costs milliseconds. For speed-of-light analysis we therefore use $\tau_x=\SI{10}{\micro s}$, a DMA-engine latency.

\section{A Speed-of-Light Bound}\label{sec:bound}
Consider any policy that keeps at most $c$ experts per layer on the GPU. Each routed-expert execution is served in one of three ways: from GPU memory (cost $a=s/\eta_gB_g$ for an expert of $s$ bytes), by fetching it and then running it on the GPU (cost $p+a$ with $p=s/\eta_pB_p$, serial with the layer), or on the CPU concurrently with the GPU (cost $b=s/\eta_cB_c$). With $m_f$ fetched and $m_c$ CPU executions out of $k$ in a layer step, the layer takes at least
\begin{equation}
g(m_f,m_c)=\max\big((k-m_c)\,a+m_f\,p,\; m_c\,b\big).
\end{equation}
$g$ is convex, being a maximum of affine functions. \textbf{Bound.} Let $M^\star$ be the minimum total number of misses any policy can incur on the trace with per-layer capacity $c$. If misses may be served without admission, this is Belady's MIN with bypass~\cite{belady1966study}; we verify its optimality against exhaustive search on random small instances. Every policy has mean misses $\bar m=\bar m_f+\bar m_c\ge M^\star/N$ over $N$ layer steps, so by Jensen's inequality the mean layer time is at least
\begin{equation}
\min_{m_f+m_c\,\ge\, M^\star/N} g(m_f,m_c).
\end{equation}
Adding the dense time gives a lower bound on time per token for every policy in the class, whether static or dynamic, predictive or not. Admission traffic, hand-offs and transfer latency only add time, so dropping them keeps the bound valid.

\paragraph{When is copying an expert worth it?} Copying an expert costs $p$ once. Afterwards, each GPU execution saves $b-a$ relative to running it on the CPU. The copy pays off only if the expert is reused at least
\begin{equation}
r^\star=\frac{p}{b-a}=\frac{1/(\eta_pB_p)}{1/(\eta_cB_c)-1/(\eta_gB_g)}
\end{equation}
times while resident. $r^\star$ does not depend on the model. It is \QwenRstarLow{} for an RTX~4060 on PCIe~4\,$\times$8 with DDR5-5600, \QwenRstarMid{} for an RTX~4090 on PCIe~4 with DDR5-6000, and \QwenRstarHigh{} for an RTX~5090 on PCIe~5 with DDR5-6400. On weak GPUs, the GPU is barely faster than the CPU for expert GEMV, so almost nothing is worth copying. On PCIe~5 with a fast GPU, one reuse suffices. For the same reason, fetching a miss on the critical path ($p+a$) loses to executing it on the CPU ($b$) whenever $\eta_pB_p<\eta_cB_c$, which holds on every PCIe~4 desktop we consider.

\Cref{tab:locality,fig:hits} summarise routing behaviour. Short-range reuse is strong in every model. \Cref{fig:toks} and \cref{tab:matched} convert hit rates into throughput with the validated model. Four observations follow.

\textbf{(i) Where misses execute matters more than the replacement policy.} On PCIe~4 desktops, the same LRU cache is faster with CPU-executed misses than with fetch-on-miss at every cache size (\cref{fig:toks}), because $\eta_pB_p<\eta_cB_c$ (\cref{sec:bound}). This explains why desktop users converge on llama.cpp's CPU offload rather than on fetch-based research systems. On PCIe~5 the two approach parity.

\textbf{(ii) The static layer split leaves throughput unused.} At the VRAM-matched point, llama.cpp-style layer assignment reaches \GptbigMidStaticOfSol\% of the bound for gpt-oss-120b on an RTX~4090 and \GptbigHighStaticOfSol\% on an RTX~5090. Placing the same bytes as a per-layer LRU cache with CPU-executed misses reaches \GptbigMidLruOfSol\% and \GptbigHighLruOfSol\%, a \GptbigMidLruGain$\times$ and \GptbigHighLruGain$\times$ speedup over the static split.

\textbf{(iii) The headroom left for predictors is bounded.} Once misses run on the CPU, the difference between LRU and Belady-bypass in hit rate translates into a much smaller difference in tok/s. The remaining gap to the bound (\cref{tab:matched}) caps what \emph{any} prefetcher or learned predictor can add on these platforms. Much of that remaining gap comes from CPU--GPU concurrency that the bound allows, not from misses.

\textbf{(iv) Weak GPUs gain little from any policy.} On the RTX~4060 the GPU's expert bandwidth is close to the CPU's ($r^\star$=\QwenRstarLow), so all strategies cluster near CPU-only speed. The lever there is DRAM bandwidth, not caching.

\section{Discussion}
\paragraph{For engine builders.} The bound says the first-order win on desktops is a \emph{dynamic} expert cache with CPU-executed misses and asynchronous admission, not better static placement or prediction. llama.cpp has no dynamic GPU expert cache today; community prototypes report large gains, consistent with our model. Admission should respect $r^\star$: on PCIe~4 an expert should be copied only if it is expected to be reused a few times.

\paragraph{For evaluation.} Hit rate is a poor proxy for speed when misses can execute elsewhere. Policies should be reported as a fraction of a hardware-specific bound, with the hand-off and admission costs stated. Our measurement set and model make that cheap.

\paragraph{For model design.} \Cref{eq:model} and the traces also run in reverse. Given a target platform ($B_g,B_c,B_p$, VRAM), they predict decode speed as a function of expert count, expert size, top-$k$ and shared-expert size, with locality measured rather than assumed. This points to designing MoE architectures \emph{for} a consumer memory hierarchy: for example, choosing expert granularity so that $r^\star$-worthy reuse is common. We leave this co-design, which requires training models, to future work.

\section{Limitations}
\textbf{Off-policy text.} Traces are teacher-forced on dataset responses, not on each model's own samples. Routing is exact for the given text, but self-generated text may be more predictable. \textbf{Batch 1 only}; small-batch serving unions experts across requests and weakens locality. \textbf{The model has no NUMA term} and over-predicts two-socket llama.cpp; it also has no explicit CPU core-count limit, and fitted efficiencies absorb implementation quality. \textbf{Validation is retrodictive}: the author had no hardware, so all measurements are third-party. Some are approximate or from VMs (flagged in the data), and two assume unstated DDR5 speeds. \textbf{Per-layer capacity}: the bound covers policies that partition the cache per layer; a global pool shared across layers could do better. \textbf{Numerics}: traces were computed in fp32 on CPU; GPU inference in bf16 may break near-ties differently.

\section{Conclusion}
A causal model's routing is fixed by its prefix, so exact decode traces of large MoEs can be collected on a small CPU machine. A five-parameter bytes-over-bandwidth model, fitted and held out across a dozen independent sources, predicts batch-1 decode within about a sixth. Combined with Belady and Jensen, these give a speed-of-light bound for consumer MoE inference. The bound shows that on today's desktops, where the misses execute matters more than how cleverly they are predicted.
