\author{Harshith Kantamneni\\Independent Researcher}

\begin{abstract}
Frontier-scale Mixture-of-Experts (MoE) models run on desktops only by keeping most experts in host memory. More than thirty systems now propose which experts to cache on the GPU, how to prefetch them, and where to execute the rest. What is missing is a ceiling that all of them can be measured against. We contribute three things.
\textbf{(1)} A way to record \emph{exact} decode-time routing traces without a GPU. A causal model routes each token according to its prefix alone, so teacher-forced prefill, streamed one decoder layer at a time with tensors read over HTTP, reproduces the routing of KV-cache decode exactly. We verify this against reference implementations of four architectures. With it we trace OLMoE, Qwen3-30B-A3B, gpt-oss-20b and gpt-oss-120b over four domains on a 2-vCPU, 7\,GB virtual machine.
\textbf{(2)} A six-parameter bytes-over-bandwidth model of batch-1 decode. It predicts \nRows{} published measurements from \nSources{} independent sources (\tokMin{}--\tokMax{} tok/s; \nModelsVal{} models; CPU-only, static CPU offload and PCIe demand fetch) with \cvMedian\% median error when whole sources are held out.
\textbf{(3)} A speed-of-light bound for \emph{any} expert placement policy with a per-layer GPU budget, whether demand-driven or prefetching. It combines Belady's MIN-with-bypass, a load-accounting argument and Jensen's inequality. We also give a closed-form reuse threshold $r^\star$ that says when copying an expert to the GPU can pay off.
The traces show strong short-range reuse: \QwenReuseOne\% of Qwen3's selected experts were also selected by the previous token, \QwenReuseX$\times$ the uniform rate. Long-range popularity, however, is weak and model-dependent across domains; for Qwen3, pinning experts that were popular on other domains does worse than not pinning. Under the validated model, running cache misses on the CPU beats fetching them over PCIe~4. On the platforms where a model does not fit, a per-layer LRU cache with CPU-executed misses recovers most of the gap between llama.cpp's static layer split and the bound. Code, traces and the annotated measurement set are released.
\end{abstract}

\section{Introduction}
A 120B-parameter MoE with 4-bit experts needs \SI{61}{GB} for its experts alone, while a consumer GPU has 8--\SI{32}{GB}. Running such models locally means splitting the experts between GPU memory and host DRAM. Decode speed is then set largely by where each routed expert's weights live when the router selects it.

The literature has responded with many mechanisms:
\begin{itemize}\setlength\itemsep{0pt}
\item demand fetching into an LRU cache~\cite{eliseev2023offloading};
\item activation-aware caches and prefetchers~\cite{xue2024moeinfinity,song2024promoe,hwang2024pregated,zhu2025preattention,wang2026seqmoe};
\item running misses on the CPU~\cite{kamahori2024fiddler,ktransformers,wang2026cloudgrade,huang2025cpugpu,zhong2025hybrimoe};
\item mixed-precision or substitute experts~\cite{tang2024hobbit,zhao2025mobile};
\item and, in practice, llama.cpp's static assignment of whole layers' experts to the CPU~\cite{llamacpp}.
\end{itemize}
Recent trace studies disagree on basic questions, such as whether a learned predictor beats LRU~\cite{zhang2026reproducible,si2026expertcache,wang2026seqmoe}. One of them notes explicitly that fewer misses need not mean higher throughput~\cite{zhang2026reproducible}.

We argue that what is missing is a \emph{bound}. For a given model, platform and GPU memory budget, how fast can batch-1 decode possibly be, and how close do the strategies people run actually get? A bound turns policy comparisons into fractions of the attainable, as the roofline model~\cite{williams2009roofline} does for kernels. Building one takes three things: routing traces of real models, a cost model that is \emph{validated} rather than assumed, and a proof that no policy in the class can beat it. This paper provides all three, using only public data and a CPU-only virtual machine.

\paragraph{Contributions.}
\begin{itemize}\setlength\itemsep{1pt}
\item \textbf{Exact traces without a GPU} (\cref{sec:traces}). Teacher-forced prefill, streamed layer by layer, matches KV-cache decode routing exactly. Each weight byte is read once per corpus instead of once per token, and never touches the disk.
\item \textbf{A validated decode model} (\cref{sec:model}). Six fitted parameters; every other input comes from datasheets and model configurations. The held-out median error is \cvMedian\% on \nRows{} published points. An ablation shows which terms matter.
\item \textbf{A speed-of-light bound and $r^\star$} (\cref{sec:bound}). A lower bound on time per token for every per-layer placement policy, including prefetchers, with a regression test against an oracle prefetcher.
\item \textbf{Findings} (\cref{sec:results}). Strong short-range locality, weak and model-dependent cross-domain popularity, a quantified advantage for CPU-executed misses on PCIe~4, and the remaining headroom for predictors.
\end{itemize}

\section{Background and Related Work}
\paragraph{MoE decode moves data.} At batch 1, a routed expert is a pair of matrix--vector products. Its cost is the size of its weights divided by the bandwidth of the memory they are read from. The data-movement view of transformers~\cite{ivanov2021datamovement} and sparsity as an efficiency lever~\cite{hoefler2021sparsity} frame MoE placement naturally: which bytes cross which link, and how often.

\paragraph{Offloading systems.} Demand-paging systems keep a per-layer GPU expert cache and copy misses over PCIe~\cite{eliseev2023offloading,xue2024moeinfinity,song2024promoe,tang2024hobbit}. Prefetchers predict the next layer's experts~\cite{hwang2024pregated,zhu2025preattention,wang2026seqmoe}. CPU-execution systems run non-resident experts on the host~\cite{kamahori2024fiddler,ktransformers,wang2026cloudgrade,huang2025cpugpu,zhong2025hybrimoe}; llama.cpp exposes this as \texttt{--n-cpu-moe} and tensor overrides~\cite{llamacpp}. MoE-Lightning~\cite{cao2024moelightning} and MoE-Lens~\cite{yuan2025moelens} model \emph{batched throughput}. We target single-user latency.

\paragraph{Caching theory and methodology.} Belady's MIN~\cite{belady1966study} minimises misses under demand paging. The interplay of prefetching and caching has been studied for file systems~\cite{cao1995prefetching}. Recent expert-cache trace studies report miss rates~\cite{zhang2026reproducible} and kernel-managed tiering on GH200~\cite{si2026expertcache}. A related study predicts llama.cpp throughput from GGUF metadata~\cite{qiu2026gguf}. We follow Hoefler and Belli's benchmarking guidelines~\cite{hoefler2015benchmarking}: medians with intervals, explicit fitted parameters, and held-out sources.

\section{Exact Routing Traces Without a GPU}\label{sec:traces}
\paragraph{Observation.} In a causal decoder, the hidden state of token $t$ at every layer is a function of tokens $1..t$ only. The experts that decode selects for token $t$ are therefore the experts that teacher-forced prefill selects at position $t$, up to floating-point ties.

\paragraph{Layer streaming.} Prefill lets us invert the usual loop order. We load \emph{one} decoder layer, push every corpus sequence through it, record the router's top-$k$ indices, free the layer, and move on. Weights are read once per corpus. The corpus's activations stay in memory ($\sim$\SI{200}{MB} for 25k tokens), and peak memory is one layer. Tensors are read straight from the model hub with HTTP range requests, so no checkpoint shard is ever stored. This matters because gpt-oss-120b's shards interleave layers and would otherwise need \SI{35}{GB} of disk. Two further details: the MoE sub-block is token-wise, so after per-sequence attention it runs once over the concatenated corpus and touches each expert once per layer; and gpt-oss experts stay MXFP4-packed and are dequantised one at a time, since a 120B layer would need \SI{13}{GB} in fp32.

\paragraph{Exactness.} Tests compare our per-layer selections with the reference \texttt{transformers} models on tiny random checkpoints of four architectures: Qwen3-MoE, OLMoE, DeepSeek-V2, and gpt-oss (both MXFP4-packed and bf16, with sequences longer than gpt-oss's 128-token sliding window). The references run both as prefill and as genuine token-by-token decode with a KV cache. All selections match exactly. For the real models, teacher-forced perplexity checks that the weights loaded correctly (\cref{tab:locality}). All traces are computed in fp32; \cref{sec:limits} quantifies how bf16 compute changes routing.

\paragraph{Corpus.} We use two-turn conversations from four public datasets: chat (UltraChat), math (NuminaMath-CoT), code (CodeFeedback) and multilingual (Aya, non-English). About 6k tokens per domain per model gives 34--36 conversations. Each is formatted with the model's own chat template and nothing else, to avoid shared-template contamination~\cite{zhang2026reproducible}. Prompt tokens are prefill; only assistant tokens are decode steps. The conversations are replayed back to back in a fixed shuffled order, as one user's session, so cache state carries across conversations and domains.

\paragraph{Cost.} Everything ran on a 2-vCPU, \SI{7}{GB} cloud VM with no GPU. Qwen3-30B-A3B (\SI{61}{GB} of bf16 weights) took about 30 minutes; gpt-oss-120b took about 75 minutes, mostly spent reading weights over the network.

\section{A Bytes-over-Bandwidth Decode Model}\label{sec:model}
\paragraph{Model.} For one decode step,
\begin{equation}
T = \frac{D + X_{g}}{\eta_g B_g} + \frac{X_{c}}{\eta_c B_c} + n_c\tau_e + \frac{X_{f}}{\eta_p B_p} + n_f\tau_x + n_h\tau_h.
\label{eq:model}
\end{equation}
$D$ is the per-token dense traffic: attention, shared experts, dense MLPs, routers, norms, the LM head and KV-cache reads. $X_g$, $X_c$ and $X_f$ are routed-expert bytes executed from GPU memory, executed on the CPU ($n_c$ expert executions), and fetched over PCIe ($n_f$ transfers). $B_g$, $B_c$ and $B_p$ are datasheet peak bandwidths of GPU memory, host DRAM (channels\,$\times$\,MT/s\,$\times$\,8\,B) and the host--device link. The $\tau$s are fixed latencies per CPU expert, per transfer and per GPU$\leftrightarrow$CPU hand-off. Byte counts are exact: each architecture is instantiated on PyTorch's \texttt{meta} device and every parameter classified. Bits per weight come from the quantisation format, or from the model's file size when the source reports it.

\paragraph{Validation data.} We collected published decode measurements that state the hardware. Each row cites its source and quotes the table or line; there are \nRows{} points from \nSources{} independent sources. They cover:
\begin{itemize}\setlength\itemsep{0pt}
\item CPU-only execution on 2- to 12-channel DDR5;
\item static CPU offload in llama.cpp, ik\_llama.cpp, KTransformers and a 2026 research engine~\cite{wang2026cloudgrade};
\item all-in-VRAM baselines;
\item demand fetch over PCIe~\cite{eliseev2023offloading}.
\end{itemize}
The \nModelsVal{} models are gpt-oss-20b and 120b, Qwen3-30B-A3B and 235B-A22B, DeepSeek-V3/R1, Kimi-K2, and Mixtral 8$\times$7B and 8$\times$22B. Four rows with unstated DRAM speed (assumed DDR5-6000), approximate web-UI readings and VM runs are flagged in the data. Two-socket runs of llama.cpp-family engines are held out before fitting (see below).

\paragraph{Fitting and held-out evaluation.} We fit $\eta$ and $\tau$ by least squares on $\log(\hat{y}/y)$ and evaluate by \emph{leave-one-source-out} cross-validation: all rows from one paper or thread are predicted by a model fitted on the rest. The demand-fetch rows come from a single paper, so they are held out one GPU at a time, giving \nGroups{} held-out groups in total. \Cref{tab:ablation} shows the ablation.
\begin{itemize}\setlength\itemsep{0pt}
\item Bytes over bandwidth plus a hand-off term (M0) already reaches \cvMZero\% median error.
\item A per-transfer latency (M1) fixes the fetch rows, because the naive whole-layer copy and the per-expert copy differ in transfer count, not in bytes.
\item A per-CPU-expert latency (M4) fixes the small-expert models on the CPU, bringing the Qwen3-30B-A3B rows to \qwenThirtyResid\%.
\item Per-layer fixed costs (M2) and a server/desktop split of $\eta_c$ (M3) do not help.
\end{itemize}
We report \selectedVariant{}, the variant with the lowest held-out MAPE. Because it was picked after seeing every variant's held-out error, its reported error is slightly optimistic; the gap to M1 is one point.

The fitted values are $\eta_g=\etaG$, $\eta_c=\etaC$, $\eta_p=\etaP$, $\tau_e=\SI{\tauE}{\micro s}$ and $\tau_x=\SI{\tauX}{ms}$. $\tau_h$ is driven to zero and absorbed by $\tau_e$. The fitted $\tau_x$ describes one Python prototype, whose bulk copies run at $\approx$87\% of PCIe peak while each per-expert copy costs milliseconds. For all bounds and projections we therefore use $\tau_x=\SI{10}{\micro s}$, a DMA-engine latency.

\paragraph{Results.} The held-out median error is \cvMedian\% (MAPE \cvMape\%), with \cvWithinTwentyFive\% of points within 25\% and the worst at \cvMax\% (\cref{fig:validation}). By execution style, the median error is \cvMedianCpu\% for CPU-only, \cvMedianStatic\% for static offload and \cvMedianFetch\% for demand fetch. Fitting a CPU efficiency per engine ranks the implementations as expected: \engOsdi{} for the 2026 AVX-512 engine~\cite{wang2026cloudgrade}, \engIk{} for ik\_llama.cpp, \engLlama{} for llama.cpp and \engKt{} for early KTransformers releases. The \nNuma{} held-out two-socket llama.cpp-family runs are over-predicted by a median of \numaMedian\%. The effect is largest for DeepSeek, whose experts are small, and small for Mixtral 8$\times$22B, whose experts are large. That points to cross-socket synchronisation per expert rather than bandwidth; the model has no term for it. The GPU-side efficiency $\eta_g$ is the least constrained parameter: only three all-in-VRAM rows pin it, and they disagree by vendor. We therefore test every projection below with $\eta_g=0.6$ as well.

\paragraph{A consistency check for dynamic caches.} One public benchmark thread~\cite{llamacppdisc24528} runs DeepSeek-V4-Flash on the same two-GPU machine with a llama.cpp fork that keeps a GPU expert cache and runs misses on the CPU. It reports hit rates of 0\%, 53\%, 76\% and 81\% at 13.61, 15.84, 17.58 and 17.66 tok/s. Our serial-cache model makes per-token time affine in the hit rate: CPU time scales with misses, and the extra GPU work for hits is small. Calibrated on the 0\% and 53\% points, it predicts \hybSeventySixPred{} and \hybEightyPred{} tok/s for the other two, errors of \hybSeventySixErr\% and \hybEightyErr\%. The fitted CPU share of time is only \hybCpuShare\%, which explains this rig's modest gains. This validates the structure of the dynamic-cache model, not its absolute scale; no public measurement of a dynamic cache states all the inputs the model needs.

\section{A Speed-of-Light Bound}\label{sec:bound}
\paragraph{Class.} Consider any policy that keeps at most $c$ of each layer's experts resident on the GPU at any time. It may be static or dynamic, demand-driven or prefetching. Every routed-expert execution runs either on the GPU from a resident copy (cost $a=s/\eta_gB_g$ for an expert of $s$ bytes) or on the CPU (cost $b=s/\eta_cB_c$). Each resident copy needs one load over PCIe (cost $p=s/\eta_pB_p$), and loads may overlap with anything.

\paragraph{Loads bound misses.} Group each expert's requests into maximal runs that are served by one resident copy. A run of $r$ requests needs one load and \emph{bridges} $r{-}1$ reuse gaps while occupying a slot. Belady's MIN with bypass maximises the number of bridged gaps under the per-layer capacity limit; its hits are exactly the bridged gaps. We verify its optimality against exhaustive search on random instances. Hence, for any policy in the class, GPU executions $\le G^\star + \text{loads}$, and so
\begin{equation}
\text{CPU executions} \;\ge\; M^\star - \text{loads},
\end{equation}
where $G^\star$ and $M^\star$ are MIN-bypass's hits and misses. A prefetcher can turn misses into hits, but each conversion costs a load.

\paragraph{Bound.} Let $x$ be the mean number of loads per layer step and $m_c$ the mean number of CPU executions. Each layer step takes at least $\max((k{-}m_c)a,\,m_cb)$ if the CPU and GPU work concurrently, or $(k{-}m_c)a+m_cb$ if they serialise. Both are convex in $m_c$, so by Jensen's inequality the mean over layer steps is at least the value at the mean $m_c\ge\max(0,M^\star/N-x)$. Across the run, the link must also carry the loads, so time per token is at least $L\,x\,p$. Minimising over $x\ge0$ gives the bound
\begin{equation}
T \ge \min_{x\ge 0}\max\Big(T_D + L\min_{m_c\ge (M^\star/N-x)^+} \ell(m_c),\; L\,x\,p\Big),
\end{equation}
with $\ell$ the concurrent or serial layer cost and $T_D$ the dense time. Hand-offs, per-transfer latency and the capacity cost of prefetching are all dropped, so the bound remains valid under the model. A regression test checks it on six platforms and three parameter sets against LRU, LFU, MIN and an optimistic oracle prefetcher that loads every MIN-bypass admission one step early; the tightest policy reaches 98\% of the bound. The static layer split and a global cross-layer pool fall outside the class, because both give some layers more than $c$ slots. We still report them for comparison. With concurrent CPU--GPU execution, the bound can exceed all-in-VRAM speed, since the CPU adds bandwidth.

\paragraph{When is copying an expert worth it?} A copy costs $p$ once. Each later GPU execution then saves $b-a$ compared with the CPU. The copy therefore pays off only if the expert is reused at least
\begin{equation}
r^\star=\frac{p}{b-a}=\frac{1/(\eta_pB_p)}{1/(\eta_cB_c)-1/(\eta_gB_g)}
\end{equation}
times while resident. $r^\star$ does not depend on the model. It is \QwenRstarMid{} for an RTX~4090 on PCIe~4 with DDR5-6000, and \QwenRstarHigh{} for an RTX~5090 on PCIe~5 with DDR5-6400. It is \QwenRstarLow{} for an RTX~4060 on PCIe~4\,$\times$8 with DDR5-5600: its narrow link makes copies expensive, and its modest memory bandwidth makes GPU execution only about twice as fast as the CPU. Likewise, fetching a miss onto the critical path (cost $p+a$) loses to running it on the CPU (cost $b$) whenever $\eta_pB_p<\eta_cB_c$ holds, as it does on the PCIe~4 platforms we consider.

\emph{Short-range reuse is strong in every model.} For Qwen3-30B, \QwenReuseOne\% of selections repeat an expert chosen by the \emph{previous} token, \QwenReuseX$\times$ the uniform-routing rate, and \QwenReuseSixteen\% repeat one chosen within the last 16 tokens. \emph{Long-range popularity is weak, and whether it transfers across domains depends on the model.} The most popular quarter of experts receives only about half of all selections. In Qwen3, the popular sets of different domains overlap \emph{less} than random sets would (Jaccard \QwenJaccard{} vs.\ \QwenJaccardRand{}). In OLMoE the overlap is somewhat above random (\OlmoeJaccard), and held-out pinning (\OlmoeHitXdom\%) does beat the layer split. In both models, pinning calibrated on the evaluation data itself (``oracle'') flatters static placement considerably.

\Cref{fig:toks} and \cref{tab:matched} turn hit rates into throughput with the validated model. Dynamic-cache rows are projections: they rest on the structural check in \cref{sec:model}, not on a direct measurement.

\textbf{(i) Where misses execute matters more than the replacement policy.} On PCIe~4, the same LRU cache is faster when misses run on the CPU than when they are fetched, because $\eta_pB_p<\eta_cB_c$ (\cref{sec:bound}). This is consistent with desktop users settling on llama.cpp's CPU offload rather than on fetch-based research systems. On PCIe~5 the two strategies move closer, and their order depends on the hand-off latency.

\textbf{(ii) The static layer split leaves throughput unused when the model does not fit.} For gpt-oss-120b on an RTX~4090, llama.cpp-style layer assignment reaches \GptbigMidStaticOfSol\% of the bound. The same bytes arranged as a per-layer LRU cache with CPU-executed misses reach \GptbigMidLruOfSol\%, which is \GptbigMidLruGain$\times$ the static split (\GptbigMidLruSeqGain$\times$ if CPU and GPU work serialise). The ranking holds with $\eta_g=0.6$.

\textbf{(iii) The headroom left for predictors is bounded.} The gap between LRU and the bound (\cref{tab:matched}) caps what \emph{any} prefetcher or learned predictor can add under per-layer capacity. The optimistic oracle prefetcher shows how much of that gap is attainable at all.

\textbf{(iv) On the RTX~4060, all strategies gain less.} $r^\star$=\QwenRstarLow{} makes copying unattractive and the GPU is only moderately faster than the CPU, so every strategy stays within a small factor of all-experts-on-CPU speed. On such a machine, DRAM bandwidth matters more than cache policy.

\section{Discussion}
\paragraph{For engine builders.} The bound says the first-order win on desktops is a \emph{dynamic} expert cache with CPU-executed misses and asynchronous admission, not better static placement or better prediction. Admission should respect $r^\star$: on PCIe~4, an expert should be copied only if it is likely to be reused a few times. We found no dynamic GPU expert cache in mainline llama.cpp; community forks that add one report gains consistent with the affine model of \cref{sec:model}~\cite{llamacppdisc24528}.

\paragraph{For evaluation.} Hit rate is a poor proxy for speed once misses can run elsewhere. Policies should be reported as a fraction of a hardware-specific bound, with hand-off and admission costs stated. The released measurement set and model make that cheap.

\paragraph{For model design.} \Cref{eq:model} and the traces also run in reverse. Given a target platform ($B_g,B_c,B_p$ and VRAM), they predict decode speed as a function of expert count, expert size, top-$k$ and shared-expert size, with locality measured rather than assumed. That suggests designing MoE architectures \emph{for} a consumer memory hierarchy. We leave this co-design, which requires training models, to future work.

\section{Limitations}\label{sec:limits}
\begin{itemize}\setlength\itemsep{1pt}
\item \textbf{Off-policy text.} Traces are teacher-forced on dataset responses, not on each model's own samples. Routing is exact for the text, but self-generated text may be more predictable.
\item \textbf{Batch 1 only.} Small-batch serving takes the union of experts across requests, which weakens locality.
\item \textbf{Unmodelled platform effects.} The model has no NUMA or cross-socket term, no core-count limit, and no DRAM contention between the CPU expert path and admission copies. Fitted efficiencies absorb implementation quality, and $\eta_g$ is weakly identified.
\item \textbf{Retrodictive validation only.} The author had no hardware, so every measurement is third-party. Some are approximate or come from VMs, and four assume unstated DDR5 speeds. Dynamic-cache projections are validated in structure only.
\item \textbf{Scope of the bound.} It covers policies with per-layer capacity; a global pool across layers could do better.
\item \textbf{Numerics.} Traces were computed in fp32 on the CPU. GPU inference in bf16 can break near-ties differently; re-tracing OLMoE with bf16 compute changes \olmoeBfDiff\% of (token, layer) expert sets and moves the 25\%-cache LRU hit rate by \olmoeBfHitDelta{} points.
\end{itemize}

\section{Conclusion}
A causal model's routing is fixed by its prefix, so exact decode traces of large MoEs can be collected on a small CPU machine without storing a single checkpoint. A six-parameter bytes-over-bandwidth model, held out source by source across \nSources{} independent sources, predicts batch-1 decode to within about a sixth. Combined with Belady, load accounting and Jensen, these give a speed-of-light bound for consumer MoE inference. The bound shows that on today's desktops, where a miss executes matters more than how cleverly it is predicted.
