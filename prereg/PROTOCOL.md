# Pre-registration: first-party measurements (phase 1)

Written and committed before any throughput or counter data exists on the
measured platform. The commit that adds this file precedes every
`results/003_*` and `results/004_*` commit on the `gpu` branch, so git history
verifies the order.

## What is fixed now

- **Predictor.** `scripts/preregister.py`, run unchanged on the job-001
  microbenchmarks. It has no parameter fitted on the new platform. The
  efficiencies and latencies come from the selected variant (M4) in
  `results/validation.json`, which was fitted on third-party data only. M0 is
  also reported, as the ablation.
- **Byte accounting.** Exact per-tensor bytes come from each GGUF header
  (`mosl/gguf_bytes.py`).
- **Platform inputs.**
  - B_g is the datasheet value.
  - B_p is the peak of the negotiated maximum link.
  - B_c is the best STREAM Triad. A VM exposes no DIMM configuration, so a
    measured number stands in for the peak the model expects. This makes
    CPU-side predictions too slow by the unknown Triad-to-peak ratio. We
    register that direction now.
- **Configurations.** These are the `SWEEP` and `NCU` tables in
  `scripts/preregister.py`: four GGUFs (gpt-oss-20b MXFP4, gpt-oss-120b MXFP4,
  Qwen3-30B-A3B Q4_K_M and Q8_0). The `n_cpu_moe` values sweep the static
  llama.cpp split, and there is a CPU-only point for each model that fits.
- **Measurement.**
  - llama.cpp is pinned to commit `2145525a`. Runs use `llama-bench -ngl 99
    -fa 1 -p 0 -n 128 -r 5`.
  - GPU clocks are locked at the maximum supported values.
  - Configurations run in one randomized order, drawn with a seed that is
    recorded.
  - Three configurations are repeated at the end to detect drift.
  - The statistic is the median over the 5 repetitions of llama-bench's
    per-repetition tok/s.
  - The thread count is chosen once, before the sweep, as the best of {8,
    nproc/2, nproc} on one CPU-heavy configuration. The rule is fixed here.
- **Counters.** Runs use `ncu --metrics dram__bytes_read.sum --cache-control
  all --clock-control none`. Bytes per token = (total at `-n 8` − total at
  `-n 4`) / 4, which cancels model load, warm-up and prompt.

## Hypotheses and pass criteria

**H0 (sanity).** No configuration beats the roofline, meaning η = 1 at the
measured device-read and STREAM bandwidths. A violation means the byte
accounting is wrong.

**H1 (byte accounting).** GPU DRAM read bytes per decode token, measured with
ncu, are within ±10 % of the GGUF-exact prediction for all four ncu
configurations.

**H2 (throughput).** The median absolute percentage error of the M4
predictions over all sweep configurations is ≤ 20 % (the static-offload
LOSO median on third-party data was 19.8 %). We also report MAPE, the maximum
error and the per-model medians.

**H3 (form).** For each model, 1/tok_s is affine in n_cpu_moe, with R² ≥
0.98. Uniform layers make the model exactly affine, so curvature would
reveal an unmodelled interaction, such as the page cache or CPU cache.

**H4 (decomposition).** Split the measured affine fit into an intercept
(the all-GPU time) and a slope (the cost per offloaded layer). Each is
compared with its predicted counterpart, and we report both errors
separately. No pass threshold is set; this is an explanatory measurement.

## Analysis rules fixed in advance

- A configuration that fails to load (out of memory) is reported as such. It
  is never dropped silently.
- Predictions are not recomputed after measurement. If the model is refitted
  on these data, that refit is reported separately as in-sample and labelled
  as such.
- Every number in the paper that comes from these runs is generated by a
  script from `results/` on the `gpu` branch.

## Outcome on the A10 (scored by `scripts/analyze_firstparty.py`; see `prereg/a10/scored.md`)

| hypothesis | result |
|---|---|
| **H0** (roofline never beaten) | **PASS**, 31/31 |
| **H1** (ncu bytes within ±10 %) | **FAIL**: measured bytes exceed GGUF bytes by 12–15 % |
| **H2** (median APE ≤ 20 %) | **FAIL**: 27.4 % |
| **H3** (affine, R² ≥ 0.98) | **PASS** on all four models (0.9965–0.9987) |
| **H4** (decomposition) | **Intercept:** over-predicted by 25–55 %. **Slope:** within 1–10 % for gpt-oss, over-predicted by 72–73 % for Qwen3. |
| **Drift** (repeats) | ≤ 0.9 % |

**H1.** The over-read is uniform across kernels: +14 % (Q8_0 head), +16 %
(Q8_0 attention) and +19 % (MXFP4 experts). ECC is enabled on this GDDR6 card
(23028 of 24576 MiB visible, i.e. inline ECC). The error is not in the
byte accounting of the weights.

**H2.** Every prediction was too slow. Two sources explain it:
- The third-party η_g (0.38) is far below this platform's (~0.58).
- η_c, relative to STREAM, is ~0.72, versus 0.60 relative to peak. We
  pre-registered this bias direction.

The per-CPU-expert latency τ_e = 20.7 µs over-predicts Qwen3's slope (k = 8).

## Pre-registration for the next platform (added before any run on it)

- **H5 (two-run calibration).** `scripts/calibrate2.py` fixes η_g from
  gpt-oss-20b at n_cpu_moe = 0 and η_c from gpt-oss-20b CPU-only. τ_e stays
  at 20.7 µs. It then predicts every other sweep configuration.
  - **Pass:** median APE ≤ 10 %.
  - **A10 reference (exploratory, post hoc):** 4.9 % median, 10.6 % MAPE,
    25.6 % max over 29 configurations.
- **H1′ (counter calibration).** The platform's DRAM over-read factor f is
  measured with ncu on the 1 GiB device-read microbenchmark of job 001:
  f = dram__bytes_read / bytes requested.
  - **Prediction:** f × GGUF bytes, within ±10 % for the ncu configurations.
