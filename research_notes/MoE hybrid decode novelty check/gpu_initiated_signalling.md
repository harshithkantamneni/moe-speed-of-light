# GPU-initiated signalling to CPU threads and fine-grained CPU-GPU hand-off inside CUDA graphs (prior art as of Sept 2026)

Scope note: the notes compare against the mechanism described in the assignment (a GPU kernel writes a mailbox into mapped pinned host memory, publishes a sequence number with `__threadfence_system`, CPU helper threads spin, compute the missed experts and answer, a GPU kernel spin-waits on the host flag with a timeout, all inside one captured decode graph, and layers where every selected expert is resident skip the hand-off). Code checks were done on shallow clones taken 2026-09-27: ktransformers HEAD c40722b (2026-09-23), llama.cpp upstream commit 2145525 (2026-09-26), ik_llama.cpp HEAD ed27bf7 (2026-09-27), PowerInfer HEAD 8bd56d6 (2026-05-11).

## Q1. CUDA mechanisms: host callbacks, stream memory ops, device polling of mapped host memory, conditional nodes, persistent kernels, and their latencies

### Takeaway
CUDA offers two different ways to put the CPU inside stream or graph order. (a) **Host-callback sync**: `cudaLaunchHostFunc` or a graph host node runs on the host, and the stream stays idle until the callback returns. (b) **Device-side polling**: a kernel spins on a flag in mapped pinned host memory, or stream memory ops such as `cuStreamWaitValue32` wait on a value. NVIDIA documents the semantics of (a) and warns against CUDA calls inside it. I found no authoritative, current microsecond figure for either path's round trip.

### Cited Findings
- `cudaLaunchHostFunc` semantics (CUDA Programming Guide, "Asynchronous Execution"): "the host function may not call any CUDA APIs"; "The stream is considered idle for the duration of the function's execution"; "Adding device work to any stream does not have the effect of making the stream active until all preceding host functions and stream callbacks have executed." The guide does not say which thread runs the callback. — [CUDA Programming Guide 2.5](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html)
- Host-callback latency anecdote (NVIDIA forum, March 2025). A user saw about **12 ms** between a callback finishing and stream 1 continuing on CUDA 12.6. NVIDIA's Robert Crovella could not reproduce it on L4/CUDA 12.2 or A40/CUDA 12.8.1. He suggested a CUDA 12.6 issue or CPU thread starvation. The thread gives no latency figures for `cuStreamWaitValue` or mapped-memory polling. — [NVIDIA Developer Forums: cuLaunchHostFunc overhead/latency + CPU->GPU signaling](https://forums.developer.nvidia.com/t/culaunchhostfunc-overhead-latency-usage-cpu-gpu-signaling/327066)
- CUDA graph conditional nodes: IF (optional else body), WHILE ("until the condition value is zero") and SWITCH ("execute the zero-indexed nth body graph once if the condition value is equal to n"). Device code sets the condition with `cudaGraphSetConditional(handle, value)`. Graphs can also be launched from the device (`cudaGraphInstantiateFlagDeviceLaunch`; fire-and-forget, tail and sibling launch). The fetched page does not give the CUDA version that introduced each node type. — [CUDA Programming Guide 4.2: CUDA Graphs](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)
- Stream memory operations (`cuStreamWaitValue32/64`, `cuStreamWriteValue32/64`, batch mem ops) are documented in the Driver API "Stream Memory Operations" group. They are the primitive behind GPUDirect Async (Agostini et al., J. Parallel Distrib. Comput.). I did not fetch these pages. — [Driver API: Stream Memory Operations](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__MEMOP.html); [GPUDirect Async: Exploring GPU synchronous communication techniques for InfiniBand clusters](https://www.sciencedirect.com/science/article/abs/pii/S0743731517303386)
- Classic latency breakdown (Lustig & Martonosi, HPCA 2013; old hardware): "cudaMemcpyAsync: 1.2µs [API call] + 6µs [driver latency] + data_size/6.8GB/s"; "cudaLaunch: 1.5µs [API call] + 3µs [driver latency]"; "cudaStreamSynchronize: 1µs". The paper argues that "up to 90% of PCIe latency comes from higher layers in the stack". It proposes hardware full/empty bits for fine-grained CPU-GPU synchronization (mean runtime improvement 26%). — [Lustig & Martonosi, "Reducing GPU Offload Latency via Fine-Grained CPU-GPU Synchronization", HPCA'13](https://mrmgroup.cs.princeton.edu/papers/dlustigHPCA13.pdf)
- A recent GPU→CPU→GPU round-trip figure through a host-memory queue, with a network operation included: the NCCL GIN Proxy backend reaches **18.0 µs** round trip for 4–128 B messages, against **16.7 µs** for the direct GPU-to-NIC path (GDAKI). — [Hamidouche et al., "GPU-Initiated Networking for NCCL", arXiv 2511.15076, Nov 19 2025](https://arxiv.org/html/2511.15076v1)
- Upstream llama.cpp explains why it avoids system-scope atomics on consumer GPUs: "atomicAdd_system() requires hostNativeAtomicSupported, which is unavailable on PCIe-attached consumer GPUs without NVLink, so the volatile path is the portable choice". A "volatile store paired with __threadfence_system() provides the release ordering". — [llama.cpp ggml/src/ggml-cuda/allreduce.cu (upstream, present at commit 2145525, 2026-09-26)](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/allreduce.cu)
- Persistent kernels and "CPU-free" execution: Unat et al.'s survey (Sept 23 2024) describes Ismayilov et al. (2023) using "persistent kernels and device-side NVSHMEM to implement fully GPU-side Jacobi 2D/3D and CG solvers". It warns that "persistent kernels can result in reduced occupancy". It notes that ROC_SHMEM "guarantees correctness when persistent kernels are being used" and "provides completely CPU-free communication mechanism". — [Unat et al., "The Landscape of GPU-Centric Communication", arXiv 2409.09874](https://arxiv.org/html/2409.09874v2)

### Inferences
- In a graph host node, the **stream (not an SM) waits**. The driver's callback thread has to wake, run the function, and let the driver re-activate the stream. In the assessed mechanism, a **kernel occupies an SM while it spins** on a host-memory flag, and CPU helper threads spin on host memory. The two therefore differ in who pays the wait: an idle stream with driver scheduling on the host, versus a busy SM with no driver in the loop. The ~84 µs/layer saving in the assignment is consistent with removing the host-driver round trips. I found no independent source quantifying a single graph host node's wake-up latency on modern drivers, so this remains an inference.
- A conditional IF node set by `cudaGraphSetConditional` is the "official" CUDA way to make a data-dependent skip inside a captured graph. The assessed mechanism does its skip inside kernels (a flag check) rather than with conditional nodes. Both are device-decided.

### Gaps
- No authoritative, recent (2024–2026) microbenchmark was found for: (a) `cudaLaunchHostFunc` / graph host-node round-trip latency; (b) `cuStreamWaitValue32` on host memory; (c) a GPU→CPU→GPU ping-pong through mapped pinned memory on PCIe Gen4/Gen5. The only modern figure is the NCCL GIN proxy's 18.0 µs, which includes network time.
- CUDA version history for conditional nodes was not verified in the fetched docs. From background knowledge (unverified here): IF/WHILE arrived in CUDA 12.3 and ELSE/SWITCH in 12.8. Batch mem-op graph nodes (`cuGraphAddBatchMemOpNode`) exist since CUDA 11.7. Using stream memory ops on host memory depends on device attributes. All of this should be checked before it is cited.

## Q2. Prior systems using GPU-initiated communication with host threads (GPU → host mailbox → CPU worker → GPU)

### Takeaway
The building block is well established and at least 16 years old. A GPU writes a request into zero-copy host memory, fences, raises a flag; a CPU thread polls, services it and writes back; the GPU spins. Examples: GPU-to-CPU Callbacks (2010), LLVM libc's GPU RPC "mailboxes", the NVSHMEM CPU proxy, the NCCL GIN Proxy backend (2025), and upstream llama.cpp's own PCIe allreduce, which spins on pinned host memory. The assessed mechanism reuses this pattern and does not invent it.

### Cited Findings
- **GPU-to-CPU Callbacks** (Stuart, Cox, Owens; UC Davis; Euro-Par 2010 workshops / Springer LNCS; GTC 2010 poster): "When issuing a callback, the GPU puts a callback request in 0-copy memory and sets a flag to alert the CPU of said request." The library "handles callbacks via polling (modern GPU drivers do not expose any interrupt/signal capabilities)". "When a GPU thread executes a synchronous callback, the GPU thread spins until the request completes"; "a threadfence() is executed to ensure that the writes to 0-copy memory are flushed". Reported service latencies were millisecond-scale: memory-manager average under 4 ms, minimum under 2 ms, maximum about 10 ms; a TCP/IP test took about 2.5 ms on the GPU against about 1 ms on the CPU. — [eScholarship PDF](https://escholarship.org/content/qt58j4v6f8/qt58j4v6f8.pdf?t=ptt3z6); [Springer chapter](https://link.springer.com/chapter/10.1007/978-3-642-21878-1_45); [GTC 2010 poster](https://www.nvidia.com/content/GTC/posters/2010/P01-GPU-to-CPU-Callbacks.pdf)
- **LLVM libc for GPUs, RPC** (Joseph Huber, AMD; LLVM Dev Mtg Oct 2023): shared "often pinned memory" holds "a buffer of memory and two mailboxes. One mailbox is write-only while the other is read-only". Ownership goes to "the client when the inbox and outbox bits are equal and to the server when they are not". "The client waits until its inbox matches its outbox". "The host periodically checks the RPC server's buffer for ports with pending work". — [libc.llvm.org: Remote Procedure Calls](https://libc.llvm.org/gpu/rpc.html); [Huber, LLVM C Library for GPUs slides](https://llvm.org/devmtg/2023-10/slides/techtalks/Huber-LibCforGPUs.pdf)
- **NVSHMEM CPU proxy vs IBGDA** (NVIDIA blog, Nov 22 2022). Proxy path: "The NVSHMEM operation writes a work descriptor to the proxy buffer, which is in the host memory". The CPU posts it to the NIC, polls the CQ, and then "notifies the GPU that the operation has completed. If GDRCopy is present, it writes a notification flag to the GPU memory directly." IBGDA drops the CPU: up to "9.5x higher throughput for NVSHMEM block-put operations with message sizes less than 1 KiB", 180 MOPS vs 1.7 MOPS. — [NVIDIA Technical Blog](https://developer.nvidia.com/blog/improving-network-performance-of-hpc-systems-using-nvidia-magnum-io-nvshmem-and-gpudirect-async/)
- **NCCL GPU-Initiated Networking (GIN), Proxy backend** (arXiv Nov 19 2025): "GPU threads enqueue operation descriptors—64-bytes ...—into lock-free queues allocated in CPU memory using fire-and-forget stores". "A dedicated CPU proxy thread per communicator, pinned to NUMA nodes near the local rank's GPU and NIC, continuously polls these queues". The proxy "updates completion state in GPU-visible memory". Round trip is 18.0 µs, against 16.7 µs for GDAKI. — [arXiv 2511.15076](https://arxiv.org/html/2511.15076v1)
- **Taxonomy**: Unat et al. separate "GPU-triggered via GPUDirect Async", where "the GPU can only initiate messages previously registered by the CPU" (stream-triggered, i.e. stream memory ops), from "device-native" GPU control (NVSHMEM-IBGDA, ROC_SHMEM). — [arXiv 2409.09874](https://arxiv.org/html/2409.09874v2)
- **Upstream llama.cpp already uses host-memory spin flags on the GPU** in its 2-GPU PCIe allreduce: "One int per (slot, rank) pair in pinned host memory. Each AR call writes a strictly increasing token ... The peer spins until its read of the other's arrival int equals the token it expects". Memory comes from `cudaHostAlloc(..., cudaHostAllocPortable | cudaHostAllocMapped)` + `cudaHostGetDevicePointer`, and thread 0 does "write token to arrival_mine; spin until arrival_other == token". This is GPU↔GPU through host memory, **not** GPU↔CPU-thread, but it uses the same primitive (a monotonically increasing sequence number, `volatile` + `__threadfence_system`). — [llama.cpp allreduce.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/allreduce.cu)
- NVSHMEM internals are covered in a June 2026 system-level analysis (not read in detail here). — [Demystifying NVSHMEM, arXiv 2606.05951](https://arxiv.org/html/2606.05951v1)

### Inferences
- Assessed against this prior art, the mailbox + seqno + `__threadfence_system` + CPU spinning helper + GPU spin-wait design is a textbook application of the "GPU-to-CPU callback / RPC mailbox / CPU proxy thread" pattern. Novelty cannot rest on the signalling mechanism. The closest structural analogues are the NCCL GIN / NVSHMEM proxy (GPU-issued descriptors, CPU proxy thread, completion flag in GPU-visible memory) and LLVM libc RPC (inbox/outbox mailboxes). There the CPU proxy runs network or libc operations; here it runs the missed experts' GEMVs.
- The prior art points to the same risks the assessed design has to handle: the SM is occupied while the GPU spins (Unat et al. on persistent kernels and occupancy), forward progress depends on a live CPU thread (hence the timeout), and consumer PCIe GPUs lack host-native system atomics (llama.cpp comment).

### Gaps
- I did not verify primary sources for other well-known members of this family: GPUfs (ASPLOS 2013), GPUnet (OSDI 2014), Genesys / GPU system calls (ISCA 2018), AMD ROCm "hostcall" (device printf/malloc services), BaM (ASPLOS 2023; GPU-initiated NVMe queues, which bypass the CPU rather than calling it) and "Hummingbird". I could not identify which "Hummingbird" system the assignment meant and found no source.
- DeepEP (DeepSeek, 2025) is widely described as having its CPU busy-wait on a GPU-written, host-mapped received-token counter in "normal" mode, which makes that mode unfriendly to CUDA graphs. That is the reverse direction (GPU→CPU signal) and directly MoE-related. The README fetch was blocked (permission timeout), so the claim is **unverified**. Related links: [DeepEP PR #708 "host-side dispatch timeout"](https://github.com/deepseek-ai/DeepEP/pull/708), [DeepEP issue #505 num_worst_tokens](https://github.com/deepseek-ai/DeepEP/issues/505).

## Q3. LLM/MoE hybrid CPU-GPU inference systems: how do they synchronize CPU experts with the GPU (especially inside CUDA graphs)?

### Takeaway
The leading system, KTransformers (SOSP '25; also the kt-kernel backend for SGLang), puts CPU experts inside one decode CUDA graph with **host callbacks** (`cudaLaunchHostFunc` for both submit and sync) plus explicit copy nodes between pinned CPU buffers and GPU tensors. It does **not** use device-side polling of host memory. llama.cpp, ik_llama.cpp and PowerInfer drive hybrid MoE from the host through ggml backend splits. Fiddler uses plain host-driven copy→compute→copy. The 2026 community efforts (a llama.cpp expert-cache RFC, a vLLM expert-offload RFC, the colibri engine) use host-side decisions or host callbacks. No public LLM/MoE system found uses GPU→host mailbox + device spin-wait for CPU expert hand-off inside a CUDA graph.

### Cited Findings
- **KTransformers paper (SOSP '25, Oct 13–16 2025, Seoul)**, verbatim: "A naive design must synchronize twice per MoE layer, once when the GPU sends activations to the CPU (submit) and again when the CPU returns its results (sync). These barriers break CUDA Graphs and add kernel-launch overhead. To hide the barriers, KTransformers encapsulates both submit and sync in cudaLaunchHostFunc, which lets CUDA invoke the callbacks inside the current stream. The entire decode path for one token now fits in a single CUDA Graph, eliminating host interruptions and improving decoding speed by up to 1.23×." — [KTransformers SOSP'25 PDF](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf); [ACM DL](https://dl.acm.org/doi/10.1145/3731569.3764843)
- Further KTransformers paper statements:
  - Decode per-layer CPU/GPU kernel times are "usually a few milliseconds or less per layer", which "exacerbate synchronization overheads".
  - "CPU-based operations introduce synchronization and data transfer points, which disrupt CUDA Graph continuity". torch.compile "frequently fragment[s] the graph at layer boundaries". "Llama.cpp disables CUDA Graph optimizations to avoid repeated capture overhead".
  - In the frameworks it analyzes, "kernel launch overhead still represents 21% of total GPU execution time".
  - Without Expert Deferral, "synchronization and activation transfers accounted for another 3% idle time".
  - CUDA Graph gives "a speedup of up to 1.23×" in decode and slight impact in prefill.
  - Source: [KTransformers SOSP'25 PDF](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf)
- **KTransformers / kt-kernel code (HEAD c40722b, 2026-09-23)**:
  - `CPUInfer::submit_with_cuda_stream` calls `cudaLaunchHostFunc((cudaStream_t)user_cuda_stream, (cudaHostFn_t)func, args)`. `sync_with_cuda_stream` calls `cudaLaunchHostFunc((cudaStream_t)user_cuda_stream, (cudaHostFn_t)&sync_, (void*)args)`.
  - `sync_` calls `TaskQueue::sync`, which blocks on a `std::condition_variable` until `pending <= allow_n_pending`. So the host-callback thread **blocks** until the CPU worker pool finishes, and the stream stays idle for that time.
  - Results come back through a separate stream copy, `output_gpu[current_slot].copy_(output_cpu[current_slot], non_blocking=True)`, from pinned CPU buffers. Expert ids, weights and inputs also live in CPU pinned tensors (`immediate_experts_ids_cpu`, `input_tensor_cpu`).
  - The same code has vendor shims (HIP `hipLaunchHostFunc`, MUSA, MACA, Ascend `aclrtLaunchCallback`). The Ascend comments note that queued callbacks "silently never fire" without a subscriber thread.
  - Sources: [cpuinfer.h](https://github.com/kvcache-ai/ktransformers/blob/main/kt-kernel/cpu_backend/cpuinfer.h); [task_queue.cpp](https://github.com/kvcache-ai/ktransformers/blob/main/kt-kernel/cpu_backend/task_queue.cpp); [experts_base.py](https://github.com/kvcache-ai/ktransformers/blob/main/kt-kernel/python/experts_base.py)
- **SGLang + KTransformers (kt-kernel)** integration was announced Oct 22 2025. It uses the same kt-kernel `CPUInfer` (above), and kt-kernel supports a static set of GPU-resident experts chosen by activation frequency (`generate_gpu_experts_masks(activation_freq, num_gpu_experts)`). — [LMSYS blog 2025-10-22](https://www.lmsys.org/blog/2025-10-22-KTransformers/); [SGLang issue #11425](https://github.com/sgl-project/sglang/issues/11425); [kt-kernel test_generate_gpu_experts_masks.py](https://github.com/kvcache-ai/ktransformers/blob/main/kt-kernel/test/test_generate_gpu_experts_masks.py)
- **Fiddler** (arXiv 2402.07033, Feb 2024): host-driven: "the activation can be copied from GPU memory to CPU memory and executed at CPU". "The time required to copy activation from the GPU to the CPU is negligible, accounting for less than 1% of the total latency". It makes per-expert CPU-vs-GPU decisions with no CUDA graphs or callbacks. — [Fiddler arXiv](https://arxiv.org/html/2402.07033)
- **llama.cpp upstream (2026-09-26)**: the only `cudaLaunchHostFunc` in `ggml-cuda.cu` sits in `ggml_backend_cuda_event_wait` inside `#if 0 // untested`. CUDA graphs are disabled when a `MUL_MAT_ID` fallback needs a stream sync ("the mul_mat_id fallback path synchronizes the stream, so we cannot use CUDA graphs", ref PR #18958). CPU-offloaded experts (`-ot exps=CPU`, `--n-cpu-moe`) are separate backend splits under the ggml scheduler, i.e. host-driven. — [llama.cpp ggml-cuda.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/ggml-cuda.cu); [PR #18958](https://github.com/ggml-org/llama.cpp/pull/18958)
- **ik_llama.cpp (HEAD ed27bf7, 2026-09-27)** and **PowerInfer (HEAD 8bd56d6, 2026-05-11)**: a grep for `cuStreamWaitValue`, `cuStreamWriteValue`, `cudaHostAllocMapped`, `cudaHostGetDevicePointer`, `__threadfence_system`, `ld.acquire.sys` and `cudaGraphConditional` found nothing. The only `cudaLaunchHostFunc` hit is the inherited ggml event-wait helper (ik_llama.cpp `ggml/src/ggml-cuda.cu:5308`; PowerInfer `smallthinker/ggml/src/ggml-cuda/ggml-cuda.cu:2806`). — [ik_llama.cpp](https://github.com/ikawrakow/ik_llama.cpp); [PowerInfer](https://github.com/SJTU-IPADS/PowerInfer)
- **llama.cpp RFC #24528 "MoE expert cache, VRAM caching of hot CPU-resident experts with hybrid hit/miss execution"** (GitHub user leloch, June 12 2026; the RFC says it was "predominantly generated by an AI ... working under my direction"):
  - The design keeps `MUL_MAT_ID` on the CPU: "Inside the CPU kernel, thread 0 dispatches one batched matvec over the cached (hit) rows on the GPU while the other threads compute the miss rows."
  - Residency and bookkeeping happen on the host. CUDA graphs are not mentioned.
  - Reported gains: GLM-5.1 754B on 4×RTX 3090 went from 13.96 to 17.49 tok/s (+25%); the stacked configuration took GLM-5.2 from 13.92 to 29.35 tok/s (+64.9%).
  - It was not merged as of August 2026.
  - Source: [llama.cpp Discussion #24528](https://github.com/ggml-org/llama.cpp/discussions/24528)
- **vLLM RFC #38256 "Incremental MoE Expert Offloading — GPU Cache + Async Pipeline"** (e1n00r, Mar 26 2026): misses fetch weights over PCIe. "No CPU fallback computation" is done. CUDA-graph compatibility comes from a mapping tensor updated on the host before replay (`slot_ids = mapping[topk_ids]`), so there are no host callbacks or device polling in the graph. — [vLLM issue #38256](https://github.com/vllm-project/vllm/issues/38256)
- **colibri** (hybrid CPU/GPU MoE engine), issue #431 (July 19–20 2026):
  - Planned a "one-graph decode" that embeds CPU work via `cudaLaunchHostFunc`, after reporting about 1,490 launches + 240 syncs ≈ 54 ms/token of API time on 6×RTX 5090.
  - Follow-up A/B tests called that figure a "summation illusion" (the API time overlapped with other work). Stock and optimized builds both ran at about 5.1 tok/s, and the real bottleneck was CPU expert sweeps at about 57 ms/token.
  - The one-graph PR was deprioritized.
  - Source: [colibri issue #431](https://github.com/JustVugg/colibri/issues/431)
- **FreeToken-Intel issue #253** (Sept 21 2026) looked for Level Zero/SYCL equivalents of "`cuStreamWriteValue64`/`cuStreamWaitValue64` (stream memory operations on mapped host memory) or `cudaLaunchHostFunc`" for a hybrid MoE project on Intel Arc. It was closed "not planned". — [FreeToken-Intel #253](https://github.com/Performant-Labs/FreeToken-Intel/issues/253)
- **HybriMoE** (DAC '25, arXiv 2504.05897) does hybrid CPU-GPU scheduling plus cache management for MoE. Its sync mechanism was not examined here. — [arXiv 2504.05897](https://arxiv.org/abs/2504.05897); [GitHub PKU-SEC-Lab/HybriMoE](https://github.com/PKU-SEC-Lab/HybriMoE)

### Inferences
- The closest prior art to "CPU experts inside a single decode CUDA graph" is **KTransformers (published Oct 2025)**. The claim "we fit CPU expert execution inside one CUDA graph" is therefore **not novel**. The differences are in mechanism:
  - KTransformers uses two host-function nodes per MoE layer. Its sync callback blocks a driver callback thread on a condition variable, and results move through separate H2D/D2H copy nodes over pinned buffers.
  - The assessed design has no host nodes. The GPU publishes a mailbox with a device-written seqno, CPU helpers spin, and a GPU kernel spins on the host flag, reading and merging results directly from mapped memory.
  - The assessed design may therefore avoid the driver's host-callback wake-up path and the separate memcpy nodes. This is a plausible engineering improvement over KTransformers' approach, not a new concept.
- Because KTransformers' graph is static and its host callbacks are unconditional nodes, the GPU cannot make a per-layer "skip the CPU" decision there. The host callback still runs every layer, although it could return quickly if it has no work. This comes from reading the code path; I did not measure it.
- I found no public source measuring per-layer overhead of KTransformers' host-callback approach in µs, so the assessed design's ~84 µs/layer (host-driven llama.cpp baseline) cannot be compared directly with KTransformers' per-layer callback cost.
- The llama.cpp expert-cache RFC (#24528) is the closest llama.cpp-ecosystem prior art for hit/miss hybrid execution, but it is CPU-driven (the CPU kernel dispatches GPU work). The assessed design is GPU-driven. The caller should confirm whether that RFC is the user's own work, since the local llama.cpp clone's branch is named `expert-cache`.

### Gaps
- I did not verify HybriMoE's, MoE-Lightning's, ProMoE's or Klotski's exact CPU-GPU sync implementations, whether any of them use CUDA graphs, or whether HybriMoE is built on KTransformers' CPUInfer (my background belief, unverified).
- I did not look at Apple / unified-memory hybrid approaches (M-series, GH200/GB10), so I have no source on whether any MoE runtime there uses flag-polling hand-off between CPU and GPU.
- No per-layer microsecond cost of `cudaLaunchHostFunc`-based submit/sync in KTransformers was found. The paper only gives end-to-end speedup (≤1.23× from CUDA Graph).

## Q4. Is "skip the CPU entirely when all selected experts are GPU-resident, decided on the GPU" done anywhere?

### Takeaway
No public system found makes this decision **on the GPU inside a captured graph**. Existing systems either always enqueue the CPU path (KTransformers' static host-callback nodes), decide residency on the host (llama.cpp RFC #24528, vLLM RFC #38256), or avoid CPU compute entirely (vLLM RFC: misses become PCIe weight fetches). This is an absence-of-evidence finding within the searched scope, not proof that nobody does it.

### Cited Findings
- In KTransformers/kt-kernel, `submit_with_cuda_stream` and `sync_with_cuda_stream` are enqueued as host functions on the stream for each MoE layer. GPU-resident experts are a static mask chosen from activation frequency (`generate_gpu_experts_masks`). I found no code path that elides the host callbacks based on device-side routing. — [experts_base.py](https://github.com/kvcache-ai/ktransformers/blob/main/kt-kernel/python/experts_base.py); [cpuinfer.h](https://github.com/kvcache-ai/ktransformers/blob/main/kt-kernel/cpu_backend/cpuinfer.h)
- llama.cpp RFC #24528 makes the hit/miss decision "on the host side based on a persistent cache buffer with explicit expert→slot bookkeeping". The CPU kernel's thread 0 dispatches the GPU hit work. — [llama.cpp Discussion #24528](https://github.com/ggml-org/llama.cpp/discussions/24528)
- vLLM RFC #38256 updates the expert→slot mapping on the CPU before graph replay and has no CPU fallback compute, so there is no CPU path to skip. — [vLLM issue #38256](https://github.com/vllm-project/vllm/issues/38256)
- CUDA does provide the device-decided skip primitive: an IF conditional node whose condition is set from a kernel via `cudaGraphSetConditional`. — [CUDA Programming Guide: CUDA Graphs](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)

### Inferences
- A device-side, per-layer, data-dependent bypass of the CPU hand-off inside one captured decode graph looks **undocumented in public LLM/MoE systems as of Sept 2026**. It follows naturally once the hand-off is device-initiated (a GPU-side "if" around the mailbox publish/wait). Reviewers may call it an obvious consequence of the design rather than a separate contribution. Its practical value depends on the all-resident layer fraction, which the expert-cache hit rate drives.

### Gaps
- No exhaustive search of 2026 arXiv (e.g. papers on expert caching combined with CPU compute, or "fine-grained CPU-GPU MoE" papers) was done within the tool budget. A targeted arXiv/Semantic Scholar sweep for "CUDA graph" + "CPU experts" + "conditional"/"mapped memory" is still needed before a paper claims novelty.

## Q5. Overall: is this a known pattern, and who already uses it? (synthesis for the novelty judgement)

### Takeaway
The signalling mechanism is known prior art: GPU→host mailbox, fence plus sequence flag, CPU spinning worker, GPU spin-wait on a host flag (2010 GPU-to-CPU callbacks; LLVM libc RPC mailboxes; NVSHMEM and NCCL GIN CPU proxies; llama.cpp's own host-memory spin allreduce). Putting CPU MoE experts inside a single decode CUDA graph is also prior art (KTransformers, SOSP '25, via `cudaLaunchHostFunc`). What remains potentially distinguishing is the combination: (1) replacing host-callback/host-driven sync with device-initiated mailbox + device spin-wait for per-layer CPU expert offload in LLM decode; (2) direct result merge from mapped memory without copy nodes; (3) a GPU-decided per-layer skip when all selected experts are resident. No public LLM/MoE system found does (1)–(3).

### Cited Findings
- Device-initiated host mailbox pattern: [GPU-to-CPU Callbacks, 2010](https://escholarship.org/uc/item/58j4v6f8); [LLVM libc RPC](https://libc.llvm.org/gpu/rpc.html); [NVSHMEM proxy (NVIDIA blog 2022)](https://developer.nvidia.com/blog/improving-network-performance-of-hpc-systems-using-nvidia-magnum-io-nvshmem-and-gpudirect-async/); [NCCL GIN proxy, 2025](https://arxiv.org/html/2511.15076v1); [llama.cpp allreduce.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/allreduce.cu)
- CPU experts in one decode CUDA graph via host callbacks: [KTransformers SOSP'25](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf); [kt-kernel cpuinfer.h](https://github.com/kvcache-ai/ktransformers/blob/main/kt-kernel/cpu_backend/cpuinfer.h)
- A 2026 hybrid engine considered and deprioritized one-graph decode via `cudaLaunchHostFunc`: [colibri #431](https://github.com/JustVugg/colibri/issues/431)

### Inferences
- Honest framing for a write-up:
  - "We apply the well-known GPU-initiated host RPC/proxy pattern (cf. GPU-to-CPU callbacks, NVSHMEM/NCCL-GIN proxies) to hybrid MoE decode. Unlike KTransformers' `cudaLaunchHostFunc`-based submit/sync, the GPU drives the hand-off through a mapped-memory mailbox, and layers whose experts are all resident skip it on the device."
  - The paper should cite KTransformers as the direct baseline. Ideally it should measure against a host-node variant (two `cudaLaunchHostFunc` nodes per layer plus copy nodes) inside the same llama.cpp graph, to isolate the benefit of device polling over host callbacks. Without that, the ~84 µs/layer saving is only versus llama.cpp's host-driven split path, not versus the strongest prior technique.
- Likely reviewer objections, drawn from prior art:
  - The GPU spin occupies SMs during CPU compute (occupancy concerns noted for persistent kernels).
  - Correctness depends on CPU helper liveness (timeout needed).
  - System-scope ordering on PCIe consumer GPUs relies on `volatile` + `__threadfence_system` rather than system atomics (the same choice upstream llama.cpp documents).

### Gaps
- No direct measurement exists (in any source found) comparing host-node sync and device polling of mapped memory for per-layer MoE hand-off. That comparison would be new data, but it has to be produced by the project itself.
